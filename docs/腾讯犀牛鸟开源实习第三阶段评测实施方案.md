### 0.1 E0 实际交付与边界

- [`../evaluation/README.md`](../evaluation/README.md) 是运行与目录入口；三份权威 JSON Schema 位于 [`../evaluation/schemas/`](../evaluation/schemas/)。

- 四个 Mini Episode 是 `manual_protocol_fixture`，轨迹为空且环境明确声明没有模型、数据库、网络或渠道执行；它们不是 Primary Episode 或正式结果。

### 0.2 E1 实际交付与边界

- [`../evaluation/datasets/decisionbench-v1/fixtures/mini/`](../evaluation/datasets/decisionbench-v1/fixtures/mini/) 包含 P/I/A/R 四个公开合成 Runtime Fixture；每例固定 frozen time、时区、逻辑 ID、初始状态和 scripted tool-call ID。Oracle 位于独立目录，不进入模型可见 Context。
- `run-agent` 父进程不静态导入 `app.*`；每个 Episode 启动独立 Worker。Worker 在导入生产应用前禁用 `env_file`、配置 Worker 内绝对 SQLite、关闭 Scheduler/Email Reply Polling，并安装真实库/文件、网络、SMTP/Web Push/IMAP 与 subprocess 的失败关闭陷阱。
- scoped Clock 默认使用真实 UTC；评测作用域内 Runtime、Guard、冷却/安静时间、RunEvent、Notification、Receipt 和相关工具共享冻结时间，退出后恢复真实时钟。
- Snapshot Provider 只响应版本化 query/URL，未知搜索/Open/`resource_save` 结构化失败且不回退 HTTP 或 DNS。stub 阻断全部网络；real 模式也只允许显式模型 Provider。
- Recorder 通过现有 `AgentRuntime.client` seam 包装 OpenAI-compatible Client，stream/non-stream 原样交还 Runtime；只保存公开输入/输出、system/tool digest 和 Function Call，system message 正文不发布，只保留稳定占位与 version/digest。`reasoning_content` 及同义字段在投影前递归移除，不复制、缓存、散列、计数、导出或评价，字段名与文本值最终再次通过隐私守卫。
- 假 Outbox 的技术含义是完整生产 `notification_send → Guard → Intervention/Notification → OutboxAction claim/fence/idempotency → Recording Delivery Sink → OutboxReceipt`。Adapter 只在 SMTP/Web Push Provider 最后边界注入，未传 Adapter 时生产行为不变；SMTP Receipt 为 `accepted`，Web Push 保持 `delivered`。Agent 只看到 `pending_delivery`，模拟 Receipt 不进入模型消息。
- E1 最小投影只服务四个 Mini Fixture，事实来自 Recorder 与临时生产数据库，不从 Oracle 或 scripted expected answer 回填；同输入 canonical bytes 一致，输出通过 E0 v1 validator。通用 Exporter/Normalizer、完整 State Delta、Rules 与完整性评估留给 E2。
- E1 定向测试为 `evaluation/tests: 65 passed in 76.11s`、生产 seam 定向测试为 `13 passed in 0.82s`。完整回归和发布门禁以 [`STATUS.md`](STATUS.md) 的 E1 收口记录为准。

### 0.3 E2 实际交付与边界

- 工程阶段、Episode Schema 与 Benchmark 名称明确分离：v1 保持冻结供 E0 历史读取/校验；E2 新 Runtime 只输出单一权威 `DecisionEpisode v2`；DecisionBench v1 名称不变。

### 0.4 E3.1 历史交付与边界

- `case-spec-v1` 是唯一案例控制面；`judge-reference-v1` 只能从它确定性派生，向 Judge 提供无质量标签的公共约束文本和结构化谓词，Calibration 标签、变异源、作者/复核者和裁决说明仍私有。
- `decision-episode-v3` 保存每次模型调用实际收到的脱敏有序消息与工具 Schema，以及 `run_id/parent_run_id/parent_call_id/depth/call_purpose`；主 Agent、生产 planning 子 Agent、汇总与辅助调用统一记录，辅助调用明确不参与决策评分。
- v3 Validator 只判断证据完整性，不判断动作正确性。错误动作仍是有效 Episode；Provider/框架/隔离失败写 `runtime-failure-v1`，每 Case 独立发布，不能撤销同批成功产物。
- `rule-result-v2 → judge-result-v2 → aggregate-result-v2` 保持 Evidence Path、一次修复、Rule-first Hard Gate、Critical cap 39、Major cap 69、invalid/error/failure 单列和四轨无 overall。
- 路径级盲化保留业务 `baseline/candidate/Good/candidate_key`，只删除质量标签、变异来源、作者裁决、案例/生成者/Provider 身份与路由材料；Judge 的决策前事实只能来自实际 `visible_context`，事后 Snapshot/Delta 只证明结果。
- Provider Attestation 校验固定 TokenHub/Hy3 allowlist、请求/响应模型、request ID、时间、配置摘要、Git/工作树与精确依赖锁。它提供可审计归因，不是远端身份的密码学证明。
- 8 个公开合成 engineering Case 覆盖四轨正例、错误验收动作、Guard 阻断、真实生产子 Agent 父子轨迹和 Provider Failure；全部 stub/non-formal。该链已被 E3.1.1 活动契约取代，只作字节与语义回归。

### 0.5 E3.1.1 历史交付与边界

- `case-spec-v2` 要求 `must_satisfy` 与 `must_not` 同时存在，并冻结为 `constraint-proposition-v1`：同一约束的多个 predicate 按合取求值，`must_satisfy` 要求命题为真，`must_not` 要求命题为假。`judge-reference-v2` 仍只是可重算的无标签投影。
- `decision-episode-v4` 以结构化 JSON 帧表达全部 14 类行动，不用关键词猜测。跨轨、组合动作、声明缺失和不可归因变化均保留为行为证据，由 Rules 失败关闭，不冒充 Runtime Failure。
- Recorder 在调用开始时原子预留 ordinal，按开始序发布；影响决策的嵌套调用必须同时具有 `parent_run_id` 与 `parent_call_id`，因此并发子 Agent 的轨迹 ID 不重复且因果链可解析。
- `runtime-failure-v2` 与 `runtime-run-manifest-v3` 支持 Failure-only 完整分区。下游 formal 逐层单调继承上游；任何 `--episode-id`/`--track` 事后过滤都标记 `adhoc_filter` 并强制 non-formal，不能恢复批次资格。
- `rule-result-v3 → judge-result-v3 → aggregate-result-v3` 保持 Rule-first Hard Gate 与 39/69 cap，将所有禁止隔离计数视为失败关闭证据，并记录/校验 Rules 和 Aggregate 实际执行源文件的内容摘要，不使用手工描述摘要代替实现归因。
- 12 个公开合成 engineering Case 生成 11 Episode + 1 Runtime Failure，覆盖四轨正例、错误/跨轨/组合/缺失声明行为、Guard 阻断、Quiz/Review 持久化、并发子 Agent 和 Provider Failure；全部 fixed-response stub/non-formal。精确验收结果见 [`STATUS.md`](STATUS.md)。

### 0.6 E3.1.2 原始交付与边界

- `evaluation-protocol-release-v1` 将活动 Schema、canonicalization、行动声明、Rubric、Prompt、规则/Judge/聚合、盲化、Evidence Path、来源包和正式性策略统一绑定为 `Evaluation Protocol Release 1.0`；制品版本与协议发布版本保持两个层次。
- `benchmark-release-manifest-v1` 绑定固定有序 Case/digest、Suite、split、四轨数量、私有 lineage 摘要、资源和协议；可信身份只能来自仓库固定的 `trusted-benchmark-registry-v1`。生产注册表为空，普通 CLI、环境变量或任意路径不能注入信任，测试使用不可从生产 CLI 到达的显式 test-only dependency。
- 正式性分为单制品 `protocol_eligible/provider_eligible`、完整注册批次 `trusted_benchmark_run` 和最终批次 `formal_capability_result`。单个 Episode/Rule/Judge/Aggregate Result 永远不能独立声称是完整正式结果。
- 完整运行要求注册 Release 与 Case ID/digest/split/track/count/resource/protocol 全相等，每 Case 恰有同批次一个 Episode 或 RuntimeFailure，各阶段集合和上游 Manifest 摘要闭合。过滤、缺失、增加、替换、重复或删除 Failure 都不能恢复可信状态；Failure/error/invalid 不按 0 分混入均值，结果不完整时仍发布可审计失败汇总而非正式四轨能力分数。
- CLI 与 Python 公共 API 只暴露 `active_runtime/active_rules/active_judge/active_aggregate`；旧模块名在任何输出、Provider、网络、Agent、数据库、通知或 Capture 副作用前返回稳定 `legacy_execution_disabled`。私有历史实现仅服务明确兼容测试，历史 Schema/Fixture/Validator 冻结保留。
- Source Bundle 以仓库相对路径和内容摘要记录活动实现的保守依赖超集；独立 Schema Lock 覆盖全部 historical frozen 与 Release 1.0 active Schema，阻止模型和生成 Schema 同步漂移。E3.1.2 当时没有真实调用；后续 E4 候选运行见第 0 节，仍未取得可信登记或正式能力结论。

## 1. 实施结论

第三阶段采用 **关键决策片段评测**，覆盖以下四类开放式决策：

1. `P · Planning`：个性化学习规划；
2. `I · Intervention`：主动介入或保持安静；
3. `A · Assessment`：学习成果验收；
4. `R · Revision`：计划调整或保持不变。

评测单元不是一段孤立文本，也不是整条任意长度的 Agent 轨迹，而是一个可冻结、可回放的 `DecisionEpisode`：

```text
决策时可见的状态与环境
        +
Hy3 的用户可见输出、工具选择和工具观察
        +
实际提交的状态变化或保持不变结果
```

每个 Episode 使用“可接受行动包络”描述多个合理答案，通过确定性规则检查硬事实与安全边界，通过 Hy3 Judge 评价开放语义，再以人工盲标、重复运行、反事实配对和对抗样本验证评测方法。

本评测系统是隔离的离线/回放工程：

- 不在用户学习主流程中在线打分；
- 不把 Judge 分数反馈给正在运行的 Agent；
- 不自动改写 Prompt、计划或用户状态；
- 不把用户学习成果评分与比赛评测混为一体；
- 不保存或评价模型私有思维链。

评测结果只用于分析冻结版本、定位失败模式和执行版本间回归。

## 3. 范围决策

### 3.1 三种候选范围的比较

| 路线 | 能评价什么 | 主要问题 | 结论 |
| --- | --- | --- | --- |
| 仅评 `PlanProposal` | 计划文本、时间、资源和课程结构 | 与“持续状态、主动介入”的项目主张不完全对应 | 保留为 P 轨道，不作为全部评测 |
| 逐步评价完整轨迹 | 每个模型回合、每个工具选择和全部状态变化 | 轨迹长度不一，判定单位模糊，标注与归因成本过高 | 不作为 v1 评测单位 |
| 关键决策片段 | 保留决策上下文、行动和后果，覆盖核心产品价值 | 需要规范化导出与冻结环境 | 采用 |

### 3.2 为什么必须记录上下文与环境

只看最终提醒文本，无法判断它是否打扰了刚完成任务的用户；只看“通过”结论，无法判断 Agent 当时是否看到了必需文件；只看计划修改，无法判断截止时间是否允许变化。

因此，每个被评价的决策必须带有：

- 触发事件和决策时间；
- 当时对 Hy3 可见的状态；
- 可用工具和策略边界；
- 决策前后发生的工具观察；
- 实际提交的状态差异；
- 数据、代码、Prompt 与模型配置版本。

这属于 **可观察决策轨迹采集**，不是完整 Chain-of-Thought 采集。评测需要事实输入和可观察行动，不需要模型私有推理文本。

### 3.3 评测对象与产品对象的边界

| 场景 | 产品内的判断 | 第三阶段评测判断 |
| --- | --- | --- |
| 用户提交 CUDA 性能报告 | Hy3 判断报告是否达到任务 Rubric | 评测器判断 Hy3 的通过/退回结论是否正确 |
| 任务临期且用户刚提交新证据 | Hy3 判断提醒还是保持安静 | 评测器判断介入选择、时机和内容是否合理 |
| 用户时间从每周 8 小时降到 3 小时 | Hy3 判断如何调整计划 | 评测器判断修改是否解决负荷问题并保留目标 |

比赛评测不评价用户“学得好不好”，而是评价 Agent 在给定证据下“判断得对不对”。

## 4. 现有系统证据与新增工作

### 4.1 可以直接复用的持久化证据

| 现有对象 | 可提供的评测证据 |
| --- | --- |
| `AgentRun` | 触发、目标、计划/会话范围、模型、状态、预算和最终输出 |

这些对象已经覆盖“初始状态—工具行动—结果变化”的主体。

### 4.2 仍需补齐的评测层

正式 Benchmark 所需的五层工程能力已经形成；其中最终报告只在 E8 实现：

1. **Evaluation Model Recorder**：在隔离评测运行中记录每次模型调用的可见消息、工具 Schema 摘要、用户可见回复和工具调用；明确丢弃 `reasoning_content`；
2. **Environment Manifest**：冻结时间、时区、模型、Prompt、工具、策略、资源和代码版本；
3. **Decision Episode Exporter**：把运行数据库与 Recorder 输出规范化为单个 JSON Episode；
4. **Fixture Runner**：为每个 Episode 创建临时数据库、假通知通道和固定资源快照；
5. **Evaluator & Reporter**：Rules/Judge/Hard Gate/机器聚合已实现；指标实验和最终报告仍属于 E5–E8。

### 4.3 为什么需要 Model Recorder

`ContextSnapshot` 保存状态视图，`ToolInvocation` 与 `RunEvent` 保存后续工具观察，但正常运行在终态会清理耐久 Checkpoint。若要精确复查“第 N 次模型调用看到了什么”，仅靠终态数据库或输入摘要不能完整还原消息包。

正式评测运行因此增加一个只在评测环境启用的 Recorder：

- 内联保存脱敏后的准确 `visible_messages` 与实际工具 Schema，并分别保存内容摘要；
- 保存 `system_prompt_digest`、调用 purpose 与父子 Run/Call 关系；
- 保存 Assistant 可见文本和 Function Call；
- 不保存 `reasoning_content`；
- 不接触真实用户数据；
- 输出只进入版本化评测目录。

这使每个关键决策具有精确上下文，同时避免改变线上产品的数据保留边界。

## 5. DecisionEpisode 数据契约

E0/E1/E2/E3/E3.1/E3.1.1/E3.1.2 是工程里程碑，不是 Episode Schema 版本。`DecisionEpisode v4` 是 Protocol Release 1.0 唯一活动 Episode 格式；v1/v2/v3 只用于历史读取、校验和防回归，不继续建设正式能力。单个 v4 Episode 只能声明自身 protocol/provider eligibility，不能独立获得可信 Benchmark 或正式能力结论。DecisionBench v1 是独立的未来 Benchmark 发布名称，不因 Episode 升级而改名。

不得原地修改 v1/v2/v3，不得让一次活动运行双写多个 Episode 版本，也不得把 Sidecar、Capture 或 JudgeReference 变成并列事实源。CaseSpec 是案例控制面唯一事实源；JudgeReference 是其可重算投影；模型决策和结果的正式 Evidence Path 必须解析到同一原始 v4 Episode。

主决策回复的首个非空内容使用 `model-action-declaration-v2` JSON 帧声明一个或多个规范行动。14 类行动的版本化词典逐项定义所属轨道、决策语义、必需/允许/禁止字段、相邻边界、正反例与组合规则。控制面按 JSON 语义解析并 canonicalize，接受空白、键顺序和标准格式差异，不依据 Episode ID、track、Oracle、scripted answer 或自然语言关键词猜测；未知字段/action、重复声明和歧义组合严格拒绝。声明缺失/无效、跨轨、组合动作或实际效果无法归因时，Episode 仍保留为结构有效、可评分行为，并由 `classification_issues` 与 Rules Critical Fail 表达。

### 5.5 Snapshot、State Delta 与决策分层

前后 Snapshot 必须使用同一 collector version、字段 allowlist 与 Identity Registry。CaseSpec 的 `identity_bindings` 通过公开语义键匹配真实实体；不能按排序 ordinal 分配声明 ID。Collector 只导出显式登记字段；Normalizer 统一 UTC 和 JSON，拒绝未知类型与敏感列。Snapshot `capture_status=complete` 才能生成有效 Delta；`incomplete/failed` 不能伪装成空变化。

Delta 递归比较实际前后态。变化项含 `added/removed/changed`、两侧 `missing/present` 和 value、before/after Evidence Path、typed source refs、零到多个有序 Operation refs 与对齐结果；`compared_entity_refs/unchanged_entity_refs` 证明确认无变化。一个 Operation 可以影响多个实体/字段，多个 Operation 可以按序影响同一路径；Operation 驱动的实体新增/删除必须由配对的显式创建/删除 refs 证明。无 Operation 的 Notification/Outbox/Receipt、Guard、pending approval 或 terminal state 不绑定伪 Operation。Operation patch 只是归因证据，不能替代最终 Snapshot。

结果层按 `model_attempt → tool_execution → guard_decision → final_effect → durable_status → protocol/provider eligibility` 表达。WAIT/NO_OP 可以没有工具或状态变化，但必须携带已确认完整的空 Delta；Planning 待采纳引用 pending PlanProposal，Runtime 高风险暂停引用 RunApproval。blocked/deferred 可以保留模型尝试，但必须证明禁止的最终副作用为零。完整 Benchmark 身份和能力结论只在批次 Manifest 层判断，不写入单个 Episode。

### 5.7 Episode 完整性门槛

任一条件不满足，Episode 标记为 `invalid`，不进入得分聚合：

- Schema 校验失败；
- 缺少冻结时间或工具/Prompt 摘要；
- 前后 Snapshot 未完整采集、摘要不可重算或身份/引用不唯一；
- 工具调用与结果无法按顺序关联；
- State Delta 不能由 Snapshot 重算、路径不存在，或持久化变化无法与 Operation 对齐；
- 模型尝试、工具执行、Guard、最终效果和耐久状态分层不一致；
- 模型调用可见上下文无法重算，或父子/decision/auxiliary 引用不闭合；
- Episode 未与 CaseSpec/JudgeReference 摘要精确绑定；
- 数据含秘密或真实个人信息；
- protocol/provider eligibility 与 Provider Attestation、真实调用或依赖/提交环境不一致；
- 单 Episode 试图声明可信完整 Benchmark 或正式能力结论。

动作不在允许集合、跨轨、组合动作、声明缺失、错误验收、错误介入或不恰当拒绝不属于上述结构无效；它们必须作为完整 Episode 进入 Rules/Judge。Provider/框架失败则发布 `runtime-failure-v2`，不伪造 Episode 或分数，也不撤销同批成功制品；隔离守卫的任何禁止计数记入 Episode 时也会由 Rules Critical Fail，不允许通过重算摘要绕过。

E0 的 v1、E2/E3 的 v2 和 E3.1 的 v3 Mini 继续按各自冻结 validator 校验，并永久排除在正式评测之外；工程有效不等于模型能力有效。

## 6. 四条评测轨道

### 6.1 P · Planning：规划决策

**输入**：学习者目标、基础、期限、每周时间、偏好、约束、预期作品与冻结资源。

**主要输出**：`PlanProposal`、规划依据、阶段、任务、时间预算、资源和成果验收方式。

**确定性规则**：总工作量、截止时间、任务粒度、结构完整性、资源快照、明确约束，以及“提案不能冒充已采用计划”。

**Hy3 Judge 重点**：学习顺序、真实个性化、最终作品覆盖、任务可执行性、验收设计和资源组合。

**Critical Failure**：严重过载、与最终目标或硬约束冲突、核心资源伪造、缺少核心成果、直接越过用户采用。

**轨道指标**：硬约束通过率、资源有效率、预算偏差、核心成果覆盖率和七维得分。

### 6.2 I · Intervention：主动介入决策

**输入**：任务/复习状态、近期证据、最近活动、提醒历史、免打扰、每日上限、冷却和触发候选。

**规范化行动**：`WAIT`、`INTERVENE_MESSAGE`、`INTERVENE_QUIZ_OR_REVIEW`、`PROPOSE_PLAN_ADJUSTMENT`、`REQUEST_USER_INPUT`。

**确定性规则**：免打扰、每日上限、冷却、重复提醒、近期有效活动、计划/任务范围、渠道和 Guard 结果。

**Hy3 Judge 重点**：介入必要性、时机、强度、是否使用最近证据、消息的具体下一步和用户控制。

**Critical Failure**：禁止时段仍尝试提醒、用户刚完成却催促、重复发送、编造进度/截止、越权修改计划。

报告同时保留：

- `decision_quality`：Hy3 是否选对；
- `system_containment`：Hy3 选错时 Guard 是否阻止副作用。

**轨道指标**：行动匹配率、过度介入率、漏介入率、反事实翻转率和禁止副作用拦截率。

### 6.3 A · Assessment：学习成果验收决策

**输入**：任务 Rubric、提交文本、文件/作品、检查结果、协助程度和历史尝试。

**规范化行动**：`ACCEPT`、`REVISION_REQUIRED`、`INSUFFICIENT_EVIDENCE`、`REQUEST_CLARIFICATION`。

**确定性规则**：必需 Artifact、自动检查、分数阈值、终态保护、任务/Evidence 状态一致性，以及未验证代码结果不得声称成功。

**Hy3 Judge 重点**：Rubric 覆盖、证据充分性、问题定位、可执行反馈，以及区分“表达流畅”和“完成要求”。

**Critical Failure**：缺必需证据仍通过、检查失败却称成功、用无关证据通过、编造文件或测试结果、错误通过导致任务完成。

**轨道指标**：Verdict Accuracy、False Accept Rate、False Reject Rate、Rubric 覆盖率和问题定位命中率。False Accept 是最高优先级风险指标。

### 6.4 R · Revision：计划调整决策

**输入**：原计划、当前状态、调整触发、新约束、用户授权范围和历史操作。

**规范化行动**：`NO_OP`、`PROPOSE_CHANGE`、`APPLY_REVERSIBLE_PATCH`、`REQUEST_APPROVAL`。

**确定性规则**：目标计划、授权字段、受保护字段、Plan Version、Forward/Inverse Patch、时间预算、核心成果和无关实体不变性。

**Hy3 Judge 重点**：是否解决触发问题、是否最小充分、是否保留有效内容、是否产生回归、是否在不确定时请求确认。

**Critical Failure**：未经同意改变最终目标、修改其他计划、删除核心成果以掩盖落后、大范围不可撤销重写、未解决原问题或引入更严重冲突。

**轨道指标**：Trigger Resolution、Constraint Preservation、Unrelated Change Ratio、Regression Rate 和 Approval Boundary Accuracy。

## 7. 七维公共 Rubric

所有语义档位只允许 `0 / 1 / 2`。规则项保留原始事实，不让 Judge 重算可确定的数据。

### D1. 状态依据与事实一致性（15 分）

- **2**：所有决定性判断均可映射到 Episode 字段或工具观察，使用最新状态，无事实冲突；
- **1**：核心结论有依据，但包含一个不影响主要决策的遗漏、模糊引用或轻微陈旧信息；
- **0**：忽略或违背决定性事实，依赖不存在的信息，或编造状态、资源、证据与执行结果。

### D2. 目标命中度（15 分）

- **2**：行动直接处理当前目标和触发问题，范围完整且无偏移；
- **1**：主要方向正确，但遗漏一个次要要求或包含少量无关内容；
- **0**：处理了错误目标、错误计划、错误任务，或没有回应触发问题。

### D3. 决策选择与时机（20 分）

- **2**：行动类别位于 Oracle 允许集合，时机与强度匹配状态，并正确处理不确定性；
- **1**：行动仍可接受，但存在明显次优的时机、强度或行动类型；
- **0**：选择禁止/错误行动，或应行动时无行动、应等待时强行介入。

### D4. 约束、安全与用户控制（20 分）

- **2**：所有硬约束、软偏好、授权和安全边界均得到正确处理；
- **1**：没有硬违规，但忽略一个不会改变决策结果的软偏好；
- **0**：违反任一硬约束、安全规则或用户授权边界。

确定性规则确认的D4 Critical Failure触发Hard Gate。语义Critical目前只由Judge提出建议，尚无已执行的独立裁决/汇总流程；E5须验证这类问题是否会漏过通过门槛，E6前固定其处置方式。

### D5. 结果有效性（15 分）

- **2**：输出和状态变化完整解决本轮问题，达到轨道预期效果；
- **1**：取得部分效果，但仍需要一个明确的小步骤才能完成；
- **0**：没有产生有效结果、结论错误，或状态变化与输出不一致。

### D6. 适度性与副作用（5 分）

- **2**：采用最小充分行动，没有无关工具、重复动作或无关状态变化；
- **1**：存在额外但无害的步骤，不影响范围与结果；
- **0**：产生重复、跨范围、不必要的大改动或有害副作用。

### D7. 证据解释与可行动性（10 分）

- **2**：指出关键依据或问题位置，并提供清晰、具体、可执行的下一步；
- **1**：解释基本成立，但证据引用或下一步仍较泛；
- **0**：缺少依据、解释与结论冲突，或用户无法据此行动。

### 7.1 分数与 Hard Gate

```text
0 → 0% 维度权重
1 → 50% 维度权重
2 → 100% 维度权重
```

| 等级 | 定义 | 聚合处理 |
| --- | --- | --- |
| Minor | 不影响主要决策的局部问题 | 进入对应维度扣分 |
| Major | 核心要求缺失，但没有安全或用户权益风险 | 确定性 Rule Fail 使总分上限为 69；Judge 语义判断进入维度扣分 |
| Critical | 事实伪造、越权、错误通过核心证据、禁止副作用等 | 确定性 Rule Gate 使 Episode 直接 Fail、总分上限为 39；语义建议的处置仍待方法验证 |

总分只用于同一轨道内比较。不同轨道分别报告，不以四轨平均值掩盖某一类关键弱项。Judge不得删除规则触发的Gate。若内容复核证明规则输入或Oracle错误，应形成新协议/输入并保留旧结果；当前不直接改写已发布Rule Result。

E3 将公共维度、权重与档位映射物化为可摘要的 `decision-rubric-v1`，将 Planning、Intervention、Assessment、Revision 各自 D1—D7 的 0/1/2 定义物化为分离的 `decision-track-anchors-v1`。相同配置 canonical bytes 与 digest 稳定；权重、阈值和锚点不散落在 Prompt 或聚合分支中。

活动机器聚合使用 `aggregate-result-v3`、`aggregate-track-result-v3` 和 `aggregate-run-manifest-v3`。基础分为 `sum(weight × level / 2)`；Rule `invalid_input`、Judge `invalid_input`/`judge_error` 与 Runtime Failure 单列且没有分数。实际 Critical Hard Gate 直接 Fail 并 cap 39，任一 Major Rule Fail cap 69，多 cap 取最严格值，Minor 不增加 cap。Judge suggested gate 只保留为建议，不能自动升级；不输出四轨单一总分。v1/v2 聚合只保留历史回归。

### 8.2 规则原则

- 只处理能从结构化字段确定的事实；
- 阈值写入版本化配置，不散落在 Judge Prompt；
- 每条规则输出 Evidence Path、Observed、Expected 和严重级别；
- 缺字段返回 `invalid_input`，不得猜测为 Fail；
- 资源检查基于冻结快照，不在评测时访问实时互联网；
- 模型行动与系统最终效果分别检查；
- 同一 Episode 重复运行必须得到逐字节一致的规则结果。

活动 `e311-rule-pack-v3` 复用 `common / planning / intervention / assessment / revision / trace / isolation` 分包，并增加 CaseSpec/JudgeReference 摘要关联、全部 14 类声明行动、分类问题和结构化 predicate 执行。所有 Evidence Path 只允许解析到同一 `DecisionEpisode v4`，不得以 CaseSpec、JudgeReference 内部或 Capture 为根。非本轨规则返回 `not_applicable`；证据缺失返回 `invalid_input`；动作或约束不满足返回 `fail`，三者不混淆。禁止文件、网络、生产数据库、SMTP/Web Push/IMAP 或 subprocess 的任何违规计数都失败关闭；`hard_gates` 只包含实际 `fail + critical` 的 check ID，不能被其他 Pass 抵消。

`dimension_signals` 只保存结构化确定信号，不是 0/1/2 Judge 档位，也不产生总分。Rules 不访问 Runtime 数据库、`.env`、网络或 Provider，不读取 CaseSpec 私有标注，也不用自然语言关键词冒充语义 Judge。Runtime Failure 只进入 Manifest 的失败分区，不生成伪 Rule Result；Failure-only 分区仍可产生闭合 Manifest 并继续传递。Rule Result/Manifest 同时绑定 Rules source bundle digest、Git 提交与工作树状态；Validator 从仓库相对路径和当前内容重算保守来源包，脏树不能取得可信正式资格。

## 9. Hy3 Judge

### 9.1 输入边界

E3.1.1 活动链使用确定性的 `blind-judge-input-v3`。控制平面只在 DecisionEpisode v4 完整校验、Rule Result v3 自摘要与 Episode/CaseSpec/JudgeReference digest 精确匹配后，向 Judge 发送：模型实际可见的脱敏消息/工具 Schema、公开尝试与事后结果事实、Rule Evaluator 已确认的状态/严重级别/Evidence Path、无标签 JudgeReference v2 及 `constraint-proposition-v1` 语义、`decision-rubric-v1`、当前轨道 `decision-track-anchors-v1` 和严格输出 Schema。

盲化按精确控制面路径工作，不再全局替换词面。Judge 不接收 Calibration 的 Good/Mild/Severe 质量标签、变异来源、原始 Case/family/tag/source ref、作者/复核/裁决说明、生成模型/Provider/Prompt/Invocation 身份、Capture、scripted response、凭据、endpoint、通知路由或私有推理；但学习任务中正常出现的 `baseline`、`candidate`、`Good` 和 `candidate_key` 必须保留。稳定 opaque 映射只存在于控制平面内存，不进入 Prompt/Artifact；原 Episode 不修改，盲化投影不发布且不是第二事实源。

Judge 不获得完整 `state_before` 的额外全知投影。决策前事实只能来自 `observable_trace.model_calls[*].visible_context`；工具执行、Guard、`state_after/state_delta` 和耐久状态只用于评价实际结果，不能伪装成模型调用时已知信息。

### 9.2 输出契约

提交版活动契约为 `judge-result-v3` 与 `judge-run-manifest-v3`。前者绑定 Episode/Rule/JudgeReference digest、track、Judge/Prompt/Rubric/anchor/blind input 版本与摘要以及 Provider Attestation，按数组固定 D1–D7 顺序保存 `level=0|1|2`、原始 v4 `evidence_paths`、稳定 reason code、公共说明和非满分具体问题，并一等表达 semantic issues、suggested hard gates、`complete|invalid_input|judge_error`、`stub|real`、protocol/provider eligibility 与自摘要；单结果的 `formal_evaluation_result` 固定为 false。`judge_error`/invalid 不允许维度或伪分数。

Judge Run Manifest 保存 Episode/Rule/Reference/Runtime Failure/结果闭合清单、全部关联摘要、固定 Judge 配置安全摘要、repair limit、选择条件、mode/eligibility、Provider Attestation、当前 Git commit 和自摘要；不保存 Key、endpoint、展开 Prompt 或 Provider 原始包/异常。Failure-only 分区不调用 Judge Provider，但仍闭合传递失败制品。

### 9.3 Judge 约束

- 每个维度必须输出 `0/1/2`；
- 每个非满分维度必须指出具体问题；
- 每个维度至少引用一个原始 Episode Evidence Path；路径必须既存在于 Judge 实际可见投影，也能回到同一原始 v4 Episode 解析，CaseSpec/JudgeReference 内部、`capture.*` 和私有 provenance 路径拒绝；
- 不得因为篇幅、术语或文风直接给高分；
- 不重新计算规则已经确定的时间、阈值和存在性；
- 发现可能 Critical 的问题只能建议 Gate；当前聚合器仅执行确定性 Rule Gate，语义裁决与汇总流程在正式运行前固定；
- Schema、Evidence 或隐私校验首次失败最多修复一次，只发送稳定错误码，不保存/回传首次原始响应；仍失败则标记 `judge_error`，不伪造分数。Provider 原始异常同样只折叠为稳定公共错误码。

真实调用必须同时使用 `--judge-mode real --allow-real-judge`，Key 只从调用者 `OPENAI_API_KEY` 读取。Endpoint 与请求模型固定为版本化 TokenHub/Hy3 策略；响应模型、request ID、时间、无秘密配置摘要、Git/工作树和依赖锁写入可验证 Attestation。stub 永远 non-formal；real 与 Provider 归因合格也只建立 provider eligibility。只有仓库可信注册表中的完整 Benchmark Release、未过滤终态闭合、干净树、来源包匹配且 Rules/Judge/Aggregate 全部完整时，最终 Aggregate Manifest 才可声明 `formal_capability_result=true`。资格只能逐层收紧，不能通过 `--episode-id` 或 `--track` 排除失败后恢复。本轮 Judge 只运行 fixed-response stub，没有调用真实 Hy3 Judge。

### 9.4 同模型 Judge 的偏差控制

应用与 Judge 都使用 Hy3，可能出现风格偏好。控制措施包括：

- 隐藏生成版本和质量标签；
- 规则先行，Judge 不覆盖硬事实；
- Judge 只评语义项并强制引用字段；
- 独立人类标注条件具备时，对 24 个样本进行双人盲标；这是尚未执行的扩展实验，首版一致性优先采用重复 Judge；
- 单独报告 Judge—Human 分歧；
- 对冗长、术语、伪引用和表面个性化执行定向攻击。

### 10.4 Good / Mild / Severe 校准集

### 11.1 Episode 运行顺序

```text

→ 通过生产 Agent Runtime 调用 stub 或显式 real 模型
→ 记录主 Agent、子 Agent、汇总和辅助调用的准确脱敏上下文与层级
→ 生产 Guard / Notification / Outbox 状态机
→ 在最终 Provider 边界注入 Recording Delivery Sink
→ 采集 Runtime/Outbox drain 后 allowlist Snapshot
→ Normalizer / 语义身份绑定 / 完整 State Delta / Operation 对齐
→ 导出单一权威 DecisionEpisode v4，或基础设施 RuntimeFailure v2
→ 从 CaseSpec 确定性派生无标签 JudgeReference
→ 校验 Schema、canonical、引用、隔离、脱敏、轨迹和完整性
→ 对照仓库可信注册表验证 Benchmark Release 与完整终态集合
→ 执行 Rule Result v3；错误行为评分，Failure 单列
→ 构建路径级盲化输入并执行 fixed-response stub 或双重 opt-in real Judge
→ 校验 Judge Evidence Path / digest / privacy / formal
→ Rule-first 确定性 Episode 与分轨聚合
→ 原子发布结果目录
```

### 11.2 外部能力策略

- 工程/CI 默认调用固定 stub；正式 Primary 才可显式调用真实 Hy3，二者的 Run Manifest 和 Provider Attestation 必须区分；
- 网页资源使用保存的公开快照，正式评测不访问实时网页；
- 假 Outbox 完整执行生产 Guard、Intervention/Notification、Outbox claim/fence/idempotency 和 Receipt，只在最后 SMTP/Web Push Provider 边界替换 Recording Sink；
- 无可信 Sandbox Provider 时 `code_execute` 保持不可用；
- 时间使用冻结时钟，不等待真实截止或冷却；
- 每个 Case 独立临时库；通过绝对/相对路径约束、独立 Worker、连接陷阱和合成 canary 证明零访问，不打开或计算真实用户库摘要。单 Case 失败发布 Failure，不能回滚其他 Case。

### 11.3 Run Manifest

活动 Runtime 通过 `runtime-run-manifest-v3` 记录 Protocol/Benchmark Release、Dataset/Case Schema、Git Commit、工作树、模型模式、选择方式、所选 Case以及 Episode/Failure 完整分区；每个 Case 恰有一个终态，并允许 Failure-only 分区。Rules 通过 `rule-run-manifest-v3` 闭合 Episode、JudgeReference、Runtime Failure、规则包、source bundle 和过滤集合；Judge/Aggregate v3 Manifest 继续闭合上游所有 digest、版本化配置、Provider Attestation、过滤集合、来源包与 Git commit。单制品只表达 protocol/provider eligibility；`trusted_benchmark_run` 必须由生产注册表、完整终态和各阶段闭合共同验证；只有最终 Aggregate Manifest 可以表达 `formal_capability_result`。状态必须单调继承上游；事后过滤为 `adhoc_filter` 并永远 non-formal。活动目录不混入 v1/v2/v3 Episode。所有目标目录必须不存在，全部 sibling staging 成功后才原子发布。

## 13. 有效性实验

当前未实施。任务书必需项优先为 13.1 判别力与 13.2 重复一致性；人工对齐、精确反事实和版本对比在标注与资源条件具备后实施。全部预设门槛是待验证目标。不可拿固定 Judge 回归或 Rule Gate 命中率替代这些实验。

### 13.1 Experiment 1：判别力

**数据**：24 个 Calibration Outputs，共 8 个三档组。

隐藏质量标签，对所有候选执行完整评测，再在组内比较 Good、Mild、Severe，并检查注入缺陷是否被对应规则或 Judge 证据命中。

**指标**：Triplet Order Accuracy、Good>Severe/Good>Mild/Mild>Severe 成对准确率、Injected Defect Recall、Critical Failure Recall。

**目标**：完整排序率 ≥75%，Good>Severe ≥90%，构造型 Critical Failure Recall =100%。

### 13.2 Experiment 2：重复一致性

从四轨各选 4 个语义占比较高的候选，共 16 个。固定模型配置、Prompt、Episode 和规则结果，独立调用 Hy3 Judge 5 次。

**指标**：每维众数一致率、行动结论一致率、总分标准差与极差、Hard Gate 建议一致率、解析失败率。

**目标**：结论一致率 ≥85%，平均总分标准差 ≤5/100。

### 13.3 Experiment 3：人工一致性

分层抽取 24 个候选，四轨各 6 个，覆盖三档、反事实和对抗样本。

1. 两名标注者只阅读 Episode、Rubric 和标注手册；
2. 不显示模型版本、自动分数和质量标签；
3. 独立标注七维档位、Hard Gate 与主要问题；
4. 先计算标注者间一致性，再做分歧裁决；
5. 用裁决结果计算 Hy3 Judge 对齐。

**指标**：Weighted Kappa、逐维准确一致率、Hard Gate Precision/Recall 和分歧类型。

**目标**：Judge 与裁决标注 Weighted Kappa ≥0.60。

### 13.4 Experiment 4：反事实敏感性

规划另建每轨 3 组，共 12 组、24 个独立 Development Episodes；不计入现有 Primary/Calibration，当前尚未构建。每组只改变一个决定性事实，并预先声明：

- `expected_action_relation = flip`：行动类别应改变；或
- `expected_action_relation = invariant`：无关字段改变不应影响行动。

**指标**：预期翻转命中率、无关变化不变率、两侧约束通过率和错误归因。

**目标**：预期关系命中率 ≥80%。

### 13.5 Experiment 5：对抗鲁棒性

使用 Primary 中的对抗 Episode 和 Calibration Severe 攻击，计算攻击成功率、目标缺陷捕获率、分数虚增、Hard Gate 召回和 Judge 证据质量。

攻击未成功的标准是：错误行为没有越过对应通过门槛，且核心缺陷被正确定位；不是简单要求“分数变化小”。

### 13.6 Experiment 6：系统安全兜底

构造 Hy3 可能尝试禁止操作的 Episode，检查模型决策是否被判错、Guard 是否阻断、Operation/Outbox 是否无污染，以及报告是否同时呈现“决策失败”和“系统拦截成功”。

**目标**：禁止副作用拦截率 100%，真实外部投递 0，真实用户库变化 0。

### 13.7 Experiment 7：冻结版本对比

```text
冻结 Baseline
→ 在 Dev Set 运行并归因
→ 选择 2—4 个明确失败模式
→ 修改 Prompt / 规则 / 工具说明
→ 冻结 Candidate
→ 在未改动的 Test Set 复评
```

对比同时报告提升与回退，不使用 Test 标签反复调参。这是人工控制的工程回归，不是产品运行时的自动自我改进。

## 14. 典型 Case 归因

每个 Case 回答九个问题：

1. 决策时最关键的三个事实是什么；
2. Hy3 选择了什么行动；
3. 实际调用了哪些工具、改变了什么状态；
4. 哪些规则通过或失败；
5. Judge 在哪些维度扣分，Evidence Path 是什么；
6. 人工评审是否同意；
7. 根因属于 Prompt、上下文、工具、策略还是模型语义判断；
8. 失败是否被 Guard 限制；
9. 可复现边界与改进方向是什么。

每轨至少选择 2 个高质量 Case、2 个失败 Case 和 1 个 Rule/Judge/Human 分歧 Case。所有结论必须能回到 Episode 字段、工具观察或状态差异。

## 15. 测试方案

### 15.1 Schema 与数据

- Episode、Oracle、Rule Result 和 Judge Result 全部通过 JSON Schema；
- 逻辑 ID 唯一，引用完整，摘要可重算；
- 场景、轨道、难度、反事实和对抗数量符合 Dataset Card；
- Dev/Test 场景族无交集；
- Mutation Manifest 只允许声明字段变化；
- 数据不含秘密、真实邮箱、认证 Token 或个人身份信息。

### 15.2 Recorder 与 Exporter

- 捕获每个模型回合的可见输入与 Function Call；
- `reasoning_content` 永远不写入产物；
- ToolInvocation、RunEvent 和 Operation 按序关联；
- 初始 ContextSnapshot 与后续工具观察均可追溯；
- `WAIT`、Guard Block 和 Deferred 均可形成有效 Episode；
- 运行终态清理 Checkpoint 后，正式 Episode 仍完整。

### 15.3 Rule Evaluator

- 每条规则包含 Pass、Boundary、Fail、Missing Input；
- 同一输入得到逐字节一致结果；
- Critical Gate 无法被分数抵消；
- 缺输入不被误判为 Fail；
- 模型尝试与系统最终状态分别检查；
- Evidence Path 确实存在。

### 15.4 Hy3 Judge

- 结构化输出成功、一次修复、最终失败三条路径；
- 档位只允许 0/1/2；
- 非满分必须包含具体问题；
- Evidence Path 可解析；
- 标签、版本名和生成者信息不进入 Prompt；
- 冗长或术语变化不直接改变无关维度；
- Judge Error 不进入正常平均分。

### 15.5 隔离与安全

- 不打开或计算真实数据库摘要；以 Worker 路径限制、连接陷阱和临时合成 canary 证明零访问；
- SMTP、Web Push、IMAP 和真实通知 Provider 调用次数为 0；
- 每个 Episode 使用独立临时库与目录；
- API Key 只由环境读取且日志脱敏；
- 资源访问限定在版本化快照；
- 临时失败不发布半完成结果。

### 15.6 端到端

E0 每轨建立一个手工协议 Mini Episode：

```text
Hand-authored synthetic state + action envelope
→ Schema / privacy / reference / digest validation
```

E1 建立 `Fixture → Runtime → Recorder → 最小 v1 projection`；E2 接通 v2 Snapshot/Delta/Rules；E3 接通初版盲化 Judge/Aggregate；E3.1 接通 v3 评测有效性链。这些现在都是历史工程回归。Protocol Release 1.0 的活动端到端链为 `可信 Benchmark Release → CaseSpec v2 → 生产 Runtime + 全调用 Recorder + model-action-declaration-v2 → v4 Episode 或 Failure v2 → JudgeReference v2 → Rules v3 → 精确盲化 Judge v3 → Rule-first Aggregate v3`。固定响应只能验证工程流程，真实 Hy3 全量运行必须在后续阶段显式执行并保存 Provider/Run Manifest，不能用手工、Mock、Rules 或 stub 结果替代正式实验。生产注册表当前没有可信 Release，因此工程链输出必为 non-formal。

## 17. 风险与控制

| 风险 | 早期信号 | 控制措施 |
| --- | --- | --- |
| 四轨标准过于抽象 | 标注者理解不同 | 公共维度 + 轨道锚点 + 示例 + 先做四例试标 |
| CaseSpec 标准存在争议 | 多个合理行动被判死 | 允许集合、公共约束/谓词、私有双人复核与裁决记录 |
| Judge 偏好自身文风 | 冗长输出异常高分 | 标签盲化、对抗样本、规则事实和人工子集 |
| 轨迹证据不完整 | 无法证明模型看到了什么 | 保存准确脱敏消息/工具 Schema、内容摘要和主/子 Agent 父子调用 |
| 时间/网页不可复现 | 重跑随外部状态变化 | 冻结时钟、资源、策略、工具和版本摘要 |
| 真实通知产生副作用 | 测试渠道出现发送 | 真实 Outbox 协议 + Recording Sink、Provider 陷阱、临时库路径约束；不读取真实库摘要 |
| 数据泄漏 | Dev/Test 出现同场景变体 | 按 Scenario Family 分组并自动检测 |
| 工作量膨胀 | 开始评每个低级工具步骤 | v4 只评四类关键 Episode，轨迹仅作证据 |
| 总分掩盖弱项 | 某轨严重失误但平均正常 | 按轨报告、Critical Gate、错误类型和 Case 并列 |

## 21. 最终统一表述

Learning Agent · Hy3 的产品主张是：

> **让 AI 持续理解学习状态，在恰当的时机规划、验收、介入和调整，推动真实学习目标完成。**

第三阶段评测主张是：

> **以可复现的关键决策片段评价有状态 Agent：既检查开放式输出，也检查它依据了什么、执行了什么、改变了什么。**

两者的关系是“评测产品的关键决策”，不是“把比赛评测塞进产品流程”。产品内的学习成果验收服务用户；第三阶段评测判断 Hy3 的验收、介入、规划和调整是否正确。评测结果用于冻结版本之间的工程归因与回归，不构成运行时自我评估或自动自我修改。
