## 一、项目概述

### 1.1 项目定位

Learning Agent · Hy3 是一个面向编程与技术学习者的主动式 AI 学习系统。

用户可以从一句并不完整的目标开始，例如：“我有 C++ 基础，希望两个月内学会 CUDA，并完成一个矩阵乘优化项目。”Learning Agent 会围绕这个目标持续工作：澄清关键条件、调研学习资源、提出可审阅的计划、陪伴任务执行、验收学习成果，并根据新的学习事实决定下一步行动。

项目的核心主张是：

> **让 AI 从一次性回答走向持续行动：理解目标、跟踪进度、验证掌握，并在恰当的时机主动介入。**

Learning Agent 不把一次对话当作任务终点。对话、计划、任务、作品、测验、复习和提醒共同形成持续更新的学习状态；Hy3 基于这些事实选择保持安静、教学、抽查、提醒或调整计划。

### 1.2 目标用户

项目面向希望独立学习编程与技术主题的个人用户，尤其适合：

- 有目标，但不知道如何拆解路径和选择资源的人；
- 时间有限，需要在期限内完成真实作品的人；
- 计划容易中断，希望得到持续反馈和适度督促的人；
- 希望用代码、项目、测验等证据证明学习成果的人。

典型主题包括 Python、C++、Git/Linux、数据结构与算法、CUDA、深度学习、Transformer、FastAPI 和 LLM Agent 工程。

### 1.3 项目要解决的问题

| 常见体验 | 问题本质 | Learning Agent 的设计 |
| --- | --- | --- |
| 输入目标后立即得到一张通用课程表 | AI 尚未理解基础、期限和成果要求 | 先完成高信息量澄清，再形成学习者简报 |
| 推荐很多教程和链接 | 资源真实性、难度与适配关系不清楚 | 搜索、打开、核验后再与任务建立关联 |
| 用户勾选任务即被视为“学会” | 完成动作不等于形成能力 | 核心任务必须提交作品、代码或测验证据 |
| 对话结束后 AI 失去上下文 | 无法知道进度、阻塞和计划是否需要变化 | 持续维护计划、事件、证据与复习状态 |
| 提醒只依赖固定闹钟 | 不理解“现在是否真的值得打扰” | Hy3 结合状态判断介入或保持安静 |

Learning Agent 的目标不是增加一次回答的篇幅，而是让学习计划能够真正进入执行、反馈和调整。

### 1.4 为什么需要 Hy3

技术学习中的正确行动不存在唯一答案。相同目标会因为基础、时间、设备、偏好、预算、近期表现和预期作品不同而产生不同路径；同一个逾期信号，也可能意味着需要提醒、需要降负荷，或已经有新证据因而应当保持安静。

Hy3 在项目中承担五类开放式判断：

1. 从自然语言目标中识别真实意图、缺失条件和隐含约束；
2. 结合多来源信息完成资源调研与多步学习规划；
3. 根据任务标准判断用户提交的证据是否足以证明掌握；
4. 综合计划、进度、证据和通知历史选择下一步行动；
5. 在目标或现实条件变化后提出幅度合适的计划调整。

规则系统负责确定性边界，Hy3 负责理解情境并在多个合理行动中做出选择。

## 二、设计思路

### 2.1 以学习状态驱动完整闭环

Learning Agent 将一段技术学习组织为持续循环：

```text
表达目标 → 澄清条件 → 调研资源 → 生成计划提案 → 用户确认
    ↓
任务学习 → 提交成果 → 学习成果验收 → 更新学习状态
    ↓
Hy3 主动判断 → 保持安静 / 教学 / 抽查 / 提醒 / 调整计划
    └──────────────────────────────→ 继续学习
```

计划不是静态日程，学习状态也不是单一进度条。每一次有效提交、失败、复习和用户反馈都会改变 Hy3 下一次决策所依据的事实。

### 2.2 先理解学习者，再规划内容

系统围绕真正影响方案结构的信息进行澄清：

- 目标与预期成果；
- 当前基础和可跳过内容；
- 截止时间、每周投入与单次学习时长；
- 学习方式、语言、预算和设备限制；
- 希望完成的作品及其验收方式。

Hy3 每轮只提出少量高信息量问题。条件充分后，系统生成学习者简报，并据此开展资源调研和计划设计。

### 2.3 让计划成为可审阅的提案

计划首先以提案出现，而不是直接改变用户状态。提案包含阶段、任务、时间预算、精选资源、核心成果和验收方式，并说明关键取舍。

用户可以继续讨论、要求修改或正式采用。目标、长期记忆和大范围计划变化保留用户确认权；低风险且可逆的学习操作可以由 Agent 执行，并留下可审计记录。

### 2.4 用证据推进学习，而不是用勾选制造进度

核心任务同时声明行动、产物、标准和证据要求。可接受的证据包括：

- 可运行代码、项目文件或实验结果；
- 性能对比、测试报告和结论；
- 对关键概念的解释；
- 简答测验或阶段综合考核；
- 能映射到目标能力的作品。

Hy3 依据任务 Rubric 检查提交内容，给出通过或需要修改的判断，并把结论、证据与反馈写入学习状态。后续教学、复习和主动介入据此展开。

### 2.5 主动，但有依据、有边界

后台心跳、任务临期、复习到期和长期停滞都可以触发一次主动判断。Hy3 会读取当前任务、近期证据、历史提醒和用户偏好，再决定是否介入以及采用何种强度。

主动行为受到免打扰时段、每日上限、冷却时间和用户授权边界约束。系统追求的是一次有用、及时、可执行的介入，而不是更高的通知数量。

### 2.6 三种“判断”的边界

| 模块 | 判断对象 | 作用 | 使用位置 |
| --- | --- | --- | --- |
| **学习成果验收** | 用户提交的代码、文件、回答和测验 | 判断用户是否掌握、哪里需要补救 | Learning Agent 产品主流程 |
| **关键决策评测** | Hy3 的规划、介入、验收和调整决策 | 判断 Agent 在给定状态下做得是否正确 | 第三阶段独立评测与实验 |
| **确定性 Guard** | 即将执行的工具与状态变化 | 阻止越权、重复通知和违反免打扰等行为 | Agent Runtime 安全边界 |

比赛评测不会给用户的学习水平打分。以“学习成果验收”为例，产品内的 Hy3 判断用户提交是否通过；第三阶段评测进一步判断 **Hy3 的这次验收是否有充分依据、结论是否正确、反馈是否有效**。

## 四、重点技术

### 4.1 统一的持续 Agent Runtime

用户消息、计划事件和后台心跳进入同一个 Hy3 Runtime。模型读取本轮目标与相关学习状态，选择工具、观察结果、修正判断，直到目标完成、需要用户确认或没有安全行动可做。

统一 Runtime 使“用户来问”和“AI 主动检查”共享同一套事实与能力，避免把提醒、规划和教学拆成彼此不理解的固定流程。

### 4.2 分层上下文与来源追踪

上下文由学习者画像、计划状态、近期对话、学习事件、证据和本轮工具结果组成。系统按相关性与预算选择信息，并保留来源、版本和摘要，使 Hy3 能够基于最新事实行动，也能说明判断来自哪里。

界面展示可观察的行动摘要和工具结果，不展示模型私有思维链。

### 4.3 可核验的资源调研

资源采用“发现—打开—核验—入选”流程。进入计划的资源保留来源、类型、语言、难度、内容摘要、核验时间和适配理由。外部内容被视为不可信输入，不因出现在网页中就获得执行权限。

### 4.4 证据化学习成果验收

任务 Rubric、提交内容、作品引用、评分、反馈和最终状态共同形成一条学习证据记录。核心任务缺少必要证据时不能被直接视为掌握；验收结果还会影响复习安排、能力状态和后续主动决策。

### 4.5 可恢复、可审计的工具行动

工具调用具有结构化参数和结果。数据库变更、操作补丁与事件记录共同保存；低风险写操作支持撤销，外部发送使用耐久投递机制，后台主动行为再经过免打扰、频率和冷却 Guard。

### 4.6 面向评测的关键决策片段

第三阶段将最能代表产品价值的时刻标准化为 **Decision Episode（关键决策片段）**：

```text
决策时可见状态与环境
        ↓
Hy3 的用户可见输出、工具选择与工具观察
        ↓
实际提交的状态变化或“保持安静”结果
```

每个片段记录触发原因、状态快照、冻结时间、策略与工具版本、可观察行动以及结果差异。它既保留“为什么在此时这样做”的上下文，又能被独立回放和复查。

## 五、第三阶段关键决策评测方案

### 5.1 评测对象：四类关键决策

评测围绕 Learning Agent 的完整价值链设置四条轨道：

| 轨道 | 评测问题 | 主要输出 |
| --- | --- | --- |
| **P · 规划决策** | 是否依据用户条件形成合理、可执行的学习方案 | `PlanProposal`、规划依据、资源与任务设计 |
| **I · 主动介入决策** | 此刻应保持安静还是介入；时机、强度和内容是否合适 | `WAIT` 或提醒/抽查/教学行动及消息 |
| **A · 成果验收决策** | 用户证据是否达到任务标准；问题定位与反馈是否正确 | `ACCEPT` / `REVISION_REQUIRED`、评分与反馈 |
| **R · 计划调整决策** | 新事实出现后是否应调整；修改是否解决问题且不过度 | `NO_OP`、调整建议或可审计状态变更 |

这四类决策分别覆盖“开始学什么、何时介入、是否学会、接下来如何变化”，与项目的主动学习主张直接对应。

### 5.2 评测单元：Decision Episode

一个 Decision Episode 包含四部分：

1. **状态包**：学习者、计划、任务、近期证据、通知历史和触发事件；
2. **环境清单**：冻结时间、时区、模型配置、Prompt 版本、工具清单、策略版本和资源快照；
3. **可观察轨迹**：用户可见输出、工具调用、工具结果和实际状态变化；
4. **可接受行动包络**：允许的行动类别、必须满足的条件、禁止行为、预期效果与严重错误。

开放式任务可能有多个合理答案，因此评测不要求复制唯一参考文本，而是判断结果是否落入可接受行动包络，并满足当前状态的关键约束。私有思维链既不是产品输出，也不参与评测。

### 5.3 七个公共评估维度

四条轨道共享七个维度，每条轨道为同一维度提供具体锚点：

| 维度 | 权重 | 可操作判定 |
| --- | ---: | --- |
| 事实与内容正确性 | 15 | 关键判断能对应状态包中的字段或工具观察；不存在与事实冲突的前提 |
| 学习目标与需求 | 15 | 行动直接服务当前学习目标和触发问题，不转移到无关任务 |
| 行动选择与时机 | 20 | 选择了可接受的行动类别；介入、验收或调整发生在恰当时点 |
| 约束与用户控制 | 20 | 满足时间、预算、证据门槛、免打扰、授权和计划边界 |
| 结果可用性 | 15 | 产物或状态变化解决了本轮问题，并达到该轨道的结果标准 |
| 行动适度与副作用 | 5 | 使用最小充分行动，没有重复通知、无关工具或不必要的大范围修改 |
| 解释与下一步 | 10 | 指出判断依据、问题位置和明确下一步，评审者可以复查 |
| **总分** | **100** | 语义项采用 0/1/2 锚点，确定性项由规则直接给出结果 |

轨道锚点使通用维度落到具体行为：规划轨道重点检查约束、顺序、时间和成果设计；主动轨道重点检查“介入还是等待”、时机与强度；验收轨道重点检查通过结论、证据充分性与问题定位；调整轨道重点检查触发问题是否解决、有效内容是否保留以及是否引入回归。

以下行为属于Hard Gate设计要覆盖的严重问题；目前确定性规则已直接执行Gate，Judge发现的语义问题只记录建议，处置流程须在方法验证后固定：

- 违反明确硬约束或用户授权边界；
- 在缺少必需证据时错误通过核心任务；
- 伪造资源、证据、工具结果或已执行状态；
- 在免打扰、冷却或频率限制下仍尝试不当介入；
- 未经同意改变最终目标，或修改无关计划与任务。

如果确定性 Guard 阻止了错误行动，报告会同时记录“模型决策错误”与“系统成功拦截”，避免用安全兜底掩盖模型问题。

### 5.4 Rule + Hy3 Judge 的混合评测

| 评测方式 | 负责内容 | 设计理由 |
| --- | --- | --- |
| 确定性规则 | 时间预算、资源快照、证据存在性、行动类别、通知策略、授权边界、状态差异 | 可重复、可单元测试，适合事实与硬约束 |
| Hy3 Judge | 学习顺序、介入必要性、反馈质量、调整适度性等开放语义 | 能理解上下文中多个条件及其关系 |
| 人工盲标与开发复核 | 双人独立标注、逐例复核及自动评分对齐 | 核对评测与依据证据形成的判断是否一致 |

Hy3 Judge 只接收脱敏后的 Episode、轨道 Rubric 和结构化输出约定，不看到 Good/Mild/Severe 标签。每个结论必须引用 Episode 字段或轨迹证据；解析失败不会被折算为低分，而是作为明确的评测失败记录。

### 5.5 评测样本设计

**DecisionBench（学习决策评测集）** 主体由48个应用场景与24份方法验证输出组成，共72份；另列8份评分操纵对抗扩展。统一入口为`evaluation/datasets/decisionbench-learning-v1`；旧目录保留历史版本身份。新的未见验证另版发布，不混入主体72份。

| 数据部分 | 数量 | 用途 |
| --- | ---: | --- |
| 关键决策输入 | 48 | 四轨各12例，真实Hy3执行后分别保留Episode/Failure；当前家族为探索候选 |
| 判别力校准集 | 24 | 每轨2个来源，构造三档决策并作AI内容裁决；E5严格排序6/8，部分缺陷模板相近 |
| **总计** | **72** | 同时评价应用决策与验证评测器本身 |

每条轨道的 12 个候选输入包含标准场景 4 个、困难场景 4 个、边界场景 2 个和对抗样本 2 个。场景覆盖不同技术主题、基础、期限、可用时间、学习方式、作品要求与近期学习状态；数据使用合成学习者和隔离数据库，不包含真实个人信息。

完整精确反事实套件计划另建独立 Development 场景，不计入现有 48 Primary 或 24 Calibration，当前尚未构建；E7已完成的拒绝/虚假执行及只改复习日期的四条方法控制轨迹单列，不替代这套扩展。它只改变一个决定性条件，用于检验 Hy3 是否真正读取状态。例如：

- 同一逾期任务，在“刚提交有效证据”和“持续无活动”两种状态下，应分别倾向保持安静与介入；
- 同一段流畅答案，在“必需项目文件存在”和“项目文件缺失”时，验收结论应发生变化；
- 同一学习目标，在“已有 C++ 基础”和“完全零基础”时，计划的前置内容应明显不同；
- 同一进度偏差，在“截止时间固定”和“截止时间可延后”时，调整策略应体现不同取舍。

对抗样本覆盖篇幅扩张、术语堆砌、伪造资源、表面个性化、重复提醒、以流畅解释掩盖证据缺失、以大范围重写掩盖局部问题等攻击。

### 5.6 评测执行流程

隔离运行学习助手，导出用户条件、全部助手输出、工具结果与状态变化；整理带原始位置的证据；先核验内容，再由Hy3按七维给等级、理由和引用。程序核对日期、适用的数值与版本契约，以及显式测试预期和实际结果。助手自述不能替代运行观察，明确的新复测记录可以更新旧测试结论。

七维加权满分100，重要不可用问题最高69分，真实越权、虚构完成或错误接受失败等严重问题最高39分；70分为通过线。报告分别保留自动结果、复核结果和运行无分。工程采集格式、旧动作声明及其诊断另行保存，不把格式差异直接换算为用户感知的质量失败。完整判据见仓内《学习决策评测方法》。

所有片段使用临时数据库、冻结时间和版本化资源快照；通知进入测试收件箱，网页与模型配置随实验保存。

### 5.7 评测方法有效性验证

| 实验 | 核心问题 | 主要指标 |
| --- | --- | --- |
| 判别力验证 | 能否稳定区分 Good/Mild/Severe | 三档完整排序率、Good>Severe 成对准确率、缺陷命中率 |
| 重复一致性 | 同一输入多次 Judge 是否得到接近结论 | 结论一致率、逐维档位一致率、总分标准差 |
| 人工一致性 | 自动评测是否接近独立评审 | 双人盲标、逐维二次加权Kappa、通过结论一致率 |
| 反事实敏感性 | 决定性事实改变时，结论是否按预期改变 | 成对决策翻转率、无关字段不变率 |
| 对抗鲁棒性 | 表面质量能否骗取高分 | 攻击成功率、关键问题捕获率、Hard Gate 触发率 |
| 系统安全兜底 | 错误模型行动能否被确定性边界阻断 | 禁止副作用拦截率、状态污染率 |

任务书要求至少完成判别力和一种一致性验证。首版优先判别力与重复一致性，人工确认单独记录；精确反事实、安全专项和产品版本对比作为后续扩展。以下为预设目标，不表示所有扩展实验均已完成：

| 指标 | 目标值 |
| --- | ---: |
| Good/Mild/Severe 完整排序率 | ≥ 75% |
| Good 优于 Severe 的成对准确率 | ≥ 90% |
| 构造型 Critical Failure 命中率 | 100% |
| 重复评测结论一致率 | ≥ 85% |
| 重复评测总分标准差 | ≤ 5/100 |
| Hy3 Judge 与人工标签 Weighted Kappa | ≥ 0.60 |
| 反事实预期变化命中率 | ≥ 80% |
| 禁止副作用拦截率 | 100% |

最终报告按轨道分别呈现分数、通过率和错误类型，不用一个总分掩盖“规划强但验收弱”或“会主动但过度打扰”等差异。

## 六、项目亮点

### 6.1 从回答质量走向决策质量

Learning Agent 的核心产物不是某一段文字，而是围绕长期目标连续发生的一组决策。项目同时关注 Hy3 说了什么、调用了什么、改变了什么，以及它是否知道何时不应行动。

### 6.2 主动性与克制同时进入设计

主动 Agent 的价值不由通知数量定义。状态判断、`WAIT` 决策、免打扰、冷却和最小充分行动共同构成“恰当介入”，让主动性建立在证据和用户边界上。

### 6.3 用真实学习证据连接规划与调整

作品、代码、测验和反馈不是流程末端的附件，而是计划能否继续、复习是否到期、提醒是否必要和调整是否合理的共同依据。

### 6.4 用可接受行动包络评价开放式 Agent

项目不为开放式决策虚构唯一参考答案，而是明确允许行动、必要条件、禁止行为和预期后果。这种评测表达既容纳多种合理方案，又能让不同评审者依据相同标准得出接近结论。

### 6.5 后续扩展：用反事实样本检验“是否真的读懂状态”

成对改变一个决定性事实，比单纯比较文风更能揭示 Agent 是否利用了上下文。该方法可以直接定位忽略证据、机械提醒、表面个性化和过度修改等失败模式。

## 七、测试与质量策略

第三阶段的“评测实验”用于证明评测方法可靠；软件测试用于证明应用和评测工具按设计运行。两者分别验收。

### 7.1 产品核心流程测试

| 测试对象 | 验证重点 | 通过标准 |
| --- | --- | --- |
| 目标澄清与规划 | 信息回填、提案结构、用户确认边界 | 能从模糊目标形成可审阅计划 |
| 资源调研 | 搜索、打开、核验与任务关联 | 入选资源有来源、摘要和适配理由 |
| 学习成果验收 | Rubric、作品、评分、反馈与状态更新 | 核心证据缺失时不能错误通过 |
| 主动介入 | 到期、停滞、近期证据、免打扰和冷却 | 应介入时给出具体行动，不应介入时保持安静 |
| 计划调整 | 触发问题、变更范围、用户授权和可撤销性 | 修复问题且不破坏目标和无关内容 |
| 运行恢复 | 模型超时、工具失败、页面刷新和进程恢复 | 状态明确、操作不重复、结果可追踪 |

### 7.2 评测工具测试

- Schema 测试：Episode、Rubric、Judge 结果和实验清单满足版本化结构；
- 规则边界测试：刚好满足、轻微超限、严重违反和缺失字段均有确定结论；
- 轨迹完整性测试：状态、工具观察、操作差异与最终结果能够关联；
- Judge契约测试：输出包含七维档位、证据路径、原因和具体问题；当前契约不含置信度字段；
- 数据用途检查：48个应用场景作为固定已见复测；未见验证在方法冻结后新建场景并冻结，单独报告，不把重复调用改称未见样本；
- 隔离性测试：评测不访问真实数据库、不发送真实通知、不写入用户状态；
- 报告回归测试：同一结果文件能够稳定生成表格、图表和 Case 页面。

### 7.3 真实 Hy3 与端到端验收

固定响应用于自动化回归，真实应用表现由真实 Hy3 运行证据支持。已有应用素材和四轨轨迹用于展示可运行场景与评测过程。原方案提出以下完整连续故事，现作为可选扩展保留：

```text
模糊目标 → 计划提案 → 用户采用 → 学习任务 → 提交证据
→ Hy3 验收 → 状态变化 → 后台主动判断 → 提醒或调整
→ 导出四类关键决策中的典型 Episode → 完成评测与归因
```

- 项目名称与 README 明确标注个人/活动作品。

## 八、可行性分析

### 8.1 产品能力与评测证据天然衔接

Agent 运行围绕结构化计划、学习事件、证据、上下文快照、工具调用、主动决策和操作差异组织。第三阶段新增的核心工作是定义 Decision Episode 导出与隔离回放协议，而不是为评测重建另一套产品。

### 8.2 关键决策片段控制了实验复杂度

四条轨道覆盖完整产品价值；每个 Episode 又是独立、有限、可回放的评测单元。规则负责硬事实，Hy3 Judge 只处理开放语义，逐例复核与独立人工确认共同核对评价依据，能够在项目周期内完成完整评测和有效性实验。

### 8.3 环境冻结保证复现

时间、资源、策略、工具版本、模型配置与 Fixture 摘要全部进入实验清单。正式运行不依赖等待真实截止时间，也不向真实渠道发送提醒，使同一 Episode 可以重复执行并比较版本差异。

### 8.4 评测与产品运行解耦

评测器以离线/回放工具交付，不在用户学习过程中自动给 Agent 打分或改写决策。评测发现首先用于核验判据、定位误罚与漏检，并形成失败模式和能力边界分析。开发者据此修改产品再做版本回归是一种可选工程用途，E7已完成这一补充实验；后续不把产品优化或分数上涨设为评测验收目标。

## 十二、结语

Learning Agent · Hy3 把技术学习从一次问答扩展为一段持续运行的目标协作：

它理解学习者，再提出路径；

它观察真实成果，再更新判断；

它知道何时行动，也知道何时保持安静；

它让每一次计划、验收、介入和调整都建立在可追溯的学习事实之上。

> **Learning Agent · Hy3：让 AI 不只给出学习建议，而是在恰当的时候推动学习真正发生。**
