## 1. S06：解释机制并修复

对象为 `primary-s06-p`，LLM Agent 工程主题的 Planning 案例。历史可确认的事实只有两次工具参数 `invalid_json`、第三次响应达到 16,000 输出 Token及最终运行失败；原始 malformed 参数没有留存，无法唯一还原旧失败。

现有修复只把 `PromptEnvelopeExceeded` 从通用 `internal_error` 分类为 `context_window_exceeded`，并安全导出原因。已有[独立测试](../tests/test_e4_terminal_diagnostics.py)证明小坏 JSON 可继续，大坏 JSON 可使下一请求超限；这没有解决产生坏参数或上下文膨胀的源头。

优先检查以下链条，用代码、独立反例和必要的少量真实请求区分事实与推断，再选择最小修复：

- [Runtime](../backend/app/runtime/agent.py) 的 `_call_model` / `_drain_stream`：流式拼接、输出截断和 `finish_reason` 处理。当前 `_drain_stream` 没有保留或判断 `finish_reason`；达到输出上限本身仍不足以证明历史 JSON 因截断而坏。
- 同文件 `awaiting_model`：原始工具参数随 assistant 消息进入 checkpoint，后续原样进入请求；核对重复参数错误、reasoning 和工具结果各自占用。
- [请求预算](../backend/app/core/prompt_envelope.py)：当前使用 UTF-8 字节上界估计；比较各分项与配置，区分本地保守估算拒绝、Provider 拒绝和输出截断。

修复后验证正常工具调用、合法长参数、坏/截断参数和恢复或终止行为；错误参数不得产生成功写入，原始失败继续保留。不要只再次改错误文案，也不要为 S06 添加个案分支。交付简明的“已证实原因、仍属推断、修复、验证”记录；不追求补齐无法恢复的历史载荷。
