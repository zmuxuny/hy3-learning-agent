# Harness 完整性标准

## 什么才算 Harness

本项目中的 Harness 不是一个聊天页面，也不是把按钮映射为固定 Prompt。它必须同时具备：持久目标、分层上下文、自主多轮 Runtime、可组合工具、确定性权限边界、可观察事件、失败恢复，以及主动触发能力。

System Prompt 负责告诉模型如何工作；Function Calling Schema 负责声明这次 Run 真正能执行什么；后端 Guard 才负责不可绕过的权限和数据边界。三者不能互相替代。

## System Prompt 与工具如何进入模型

`backend/app/runtime/prompt.py` 定义长期稳定的行为契约。每次 Run 还会追加触发源、目标和 `ContextAssembler` 生成的上下文快照。

`backend/app/tools/registry.py` 中每个 `ToolDefinition` 由名称、用途、Pydantic 参数模型和处理函数组成。Runtime 调用 `openai_tools()` 将这些定义转换为 OpenAI-compatible Function Calling JSON Schema，并通过模型请求的 `tools` 字段发送。工具不是写在 Prompt 里供模型“假装调用”；真正可执行能力以 Schema 和后端处理函数为准。

## 完整版必须补齐的硬能力

1. **计划原子操作**：`plan_patch`、`task_create`、版本冲突检测和跨计划协调提案。
2. **证据执行环境**：授权文件读取、提交检查、隔离代码运行、测试结果结构化回传。
3. **外部信息能力**：公开资料搜索、资源证据与来源、日历读取和受控写入。
4. **审批状态机**：Run 在高风险工具前进入 `waiting_approval`，批准后从检查点恢复，拒绝后让模型观察结果。
5. **可靠性与预算**：错误分类、幂等键、单工具重试上限、Token/时间/费用预算、进程重启恢复。
6. **上下文压缩**：Session 摘要、计划记忆巩固、相关性检索、来源引用和过期策略。
7. **主动候选生成**：先用确定性规则廉价发现逾期、停滞、复习和冲突事件，再决定是否调用 Hy3。
8. **受限子 Agent**：调研和代码评测可并行，但默认只读，由主 Agent 汇总并负责最终写操作。

## 完成顺序

参赛版本不按工具数量堆功能，按可演示闭环推进：

1. 先完成“证据提交 → 主动测验 → 评分 → 复习 → 可撤销调整”。
2. 再完成审批状态机与计划原子 Patch，使自主调整既真实又安全。
3. 接入文件/代码执行和公开资源搜索，形成类似 Codex 的受控执行能力。
4. 最后补可靠性预算、上下文压缩和子 Agent；这些完成后才称为完整 Harness。
