# 产品定义

> 状态说明（2026-08-20）：本文主要定义目标产品契约。H1–H4 已完成，累计关闭 50 个缺陷 ID、剩余 37 个 open ID，下一门禁是 H5；Context、提醒、应用部署边界和完整前端仍有阻塞缺陷。逐项状态见 [`V2_H0_DEFECT_MATRIX.md`](V2_H0_DEFECT_MATRIX.md)。H0–H8 完成前只建议受控 loopback Demo。

## 一句话描述

Learning Agent 是一个会持续维护学习上下文、主动判断是否需要介入，并通过资源、计划、证据检查、提醒和复习帮助用户真正执行计划的个人 AI Harness。

产品只面向个人电脑或个人服务器持续运行，不建设账号、组织和租户系统。单用户服务器仍必须有认证；当前稳定版本只建议 loopback 本机运行，服务器模式作为 V2 硬化门禁完成后才对外承诺。首要场景是编程和技术学习。

## 核心问题

常见 AI 学习产品依赖用户主动打开对话。对话结束后，模型不了解计划是否执行、用户在哪里受阻、什么知识应该复习，也不会主动检验学习效果。

本项目解决三个问题：

1. **计划与执行脱节**：计划必须随真实进度演进。
2. **AI 永远被动**：系统持续观察状态，并决定何时保持安静、提醒或抽查。
3. **上下文容易丢失**：用户偏好、各计划状态、历史表现和原始对话需要分层管理。

## 核心闭环

```text
建立目标，Agent 持久化已知事实与待确认问题
        ↓
Hy3 判断信息充分；必要时委派规划子 Agent
        ↓
生成可讨论的计划提案，用户显式采用
        ↓
用户执行任务并产生学习事件
        ↓
后台 Agent 周期性读取状态和记忆
        ↓
观察 → 思考摘要 → 规划 → 调用工具 → 验证结果
        ↓
保持安静 / 提醒 / 抽查 / 调整计划
        ↓
更新事件、记忆与下一次检查时间
```

## 主动的含义

后台进程持续运行，但不无限循环调用模型。出现候选事件时才调用 Hy3：

- 任务临近截止或已经逾期
- 长时间没有学习活动
- 到达间隔复习时间
- 连续失败表明用户可能受阻
- 提前完成，计划有调整空间
- 用户允许的学习时间到来
- 多个计划出现时间或优先级冲突

Hy3 读取经过组装的上下文并自主决策。系统再经过冷却时间、免打扰时段和频率限制决定是否触达用户。

当前实现是一个个人实例级的全局心跳，不是“每个任务一个定时器”。默认每 5 分钟轻量扫描所有活动计划的候选状态；到期复习、24 小时内截止任务或可配置的无学习证据时长（默认 24 小时）会产生候选。扫描本身不读取所有对话；命中后才以明确计划焦点启动 Hy3，读取该计划状态、证据与记忆并决定保持安静、提醒、询问进度或执行低风险动作。收件箱公开最近判断和下一轮时间，避免把“后台存在”当成不可验证的文案。

目标契约中，主动提醒首先是一条连续对话中的 Agent 消息，收件箱只是跨对话聚合入口；所有渠道与回复引用唯一 Intervention/Session。旧实现的活动 Run 回复会丢 target，多渠道按 delivery 重复投影，IMAP 可能在 job 提交前置 Seen（H5-INT-001–003、H5-MAIL-002）。

## 自主权模型

目标自治模型允许 Agent 通过基础工具操作计划，但权限、scope、审批、幂等和副作用状态必须由后端 Guard/UoW 强制，而不是 System Prompt。H2 已将数据库写入、幂等状态与 outbox intent 纳入同一 UoW；H3 已让审批、Runtime finalization、Queue 和 child 预算由统一状态机强制；H4 已让 Evidence eligibility、Artifact 完整性和 Competency scope/revision/dependency 由架构层强制。H5 的 Context/Intervention 与 H6 的应用部署边界仍未满足完整目标契约。

- **自动执行**：提醒、抽查、安排复习、创建通知、生成临时学习材料。
- **自动执行且可撤销**：调整任务时间、创建补救任务、重排低风险任务。
- **执行前确认**：删除数据、跨计划大规模重排、改变最终目标、写入全局长期记忆、向外部服务发送敏感内容。

用户以后可以提高自治等级，但不能关闭操作审计。

## 学习计划

创建计划不是一次性大表单。Agent 在同一个 Session 中维护 `PlanningIntake`：学习目标、当前基础、最终期限、每周可用时间、学习偏好、期望产出、可用资源和不希望采用的学习方式都可以成为事实，但并非机械必填。每轮只询问 1–3 个最影响结构的问题，并说明为什么要问；选项和自由回答通过可恢复提问卡呈现。提交卡片是结构化交互本身：答案直接进入原 Session 的隐藏交互消息，卡片立即退出待答状态，不再复制成普通用户气泡。

需求是否充分由 Hy3 判断并记录置信度、理由和假设。至少要足以形成明确目标、合理起点、可行节奏、期望产出以及带证据门槛的核心任务。信息充分后，主 Agent 可以把资源调研、课程结构与考核审查分给最多三个只读规划子 Agent；各子 Run 有独立 ID 与父 Run 关系。主 Agent 解决冲突并写入 `PlanProposal`。正式提案必须包含目标、期望产出、至少一个阶段，且每个阶段至少一个任务。提案可继续讨论或放弃，只有用户点击采用后才在同一事务中创建正式 `Plan → Stage → Task` 并建立 SessionPlanLink；已归档 Session 不能采用遗留提案。

计划采用：

```text
Plan
├── 精选学习资源
└── Stage
    ├── 学习任务
    ├── 练习
    └── 阶段考核
```

系统支持多个并行计划，由 Agent 协调时间和优先级。学习材料可以来自用户文件、联网搜索或 AI 生成内容。联网资源不是一串搜索链接：Agent 应比较结构化课程、低门槛教程、动手实验和必要参考，打开核验后记录类型、难度、语言、摘要及其为何适合当前计划，并在计划页形成可浏览清单。

归档是明确的只读生命周期，而不是仅从列表隐藏：归档计划仍可读取、检索历史和恢复，但不能新增或修改任务、提交、测验、复习、资源和计划日历。恢复后才能继续学习写入。计划或 Session 存在活动/待审批根 Run 或未处理队列时不能归档，避免运行中的上下文失效或尚未执行的用户意图被级联删除。

当用户问“我现在该做什么”或“你来教我”时，计划 Agent 先读取统一 `study_state_get` 快照：计划版本、当前阶段、当前/推荐任务、核心证据缺口、阻塞、逾期、复习与近期提交。即使所有任务仍是 pending，也会选择第一个可执行任务。随后只讲解必要概念并给出一个小练习；收到回答或证据后才推进，而不是一次性输出整门课程。

## 主动考核

首批支持：

- 简答和追问
- 编程任务或文件提交
- 阶段综合考核

普通任务允许手动完成；核心任务必须提供证据或通过考核。评分保留题目要求、用户证据、判定依据和后续建议。错误处理由 Agent 自主选择提示、追问、补救任务或间隔复习。

## 上下文与记忆

系统保存原始对话，也生成短期和长期摘要。上下文分为：

- 当前 Run 的工作记忆
- 会话原文与会话摘要
- 不可变学习事件
- 每个计划的独立记忆
- 跨计划全局短期记忆
- 经确认的全局长期画像

数据库存储结构化事实，同时生成可读 Markdown 快照。用户可以在“AI 记忆”页面查看来源和使用痕迹、确认候选、提出纠正、归档与恢复；纠正会保留新旧替代关系，公开 API 不物理删除历史认识。当前跨重启仍以 Markdown 快照为投影边界，结构化 Context Pack 与完整 source-version 重建属于 H5/M17 债务。

## 通知渠道

站内收件箱是无需外部凭据的默认渠道；浏览器通知和 SMTP/IMAP 是可选增强。H2 已要求 SMTP/WebPush 先写耐久 outbox，发送中断后保留 uncertain/needs-reconciliation，不能盲目重放；只有 workspace 文件可凭已持久化 hash 自动恢复。所有渠道共享唯一 Intervention 与 Session、邮件 reply job 耐久提交后才 ack 仍是 H5 的目标契约，不能承诺在活动 Run、归档计划或进程中断下已经满足该语义。

应用关闭或主机停机时不保证提醒；用户需要让本地服务持续运行。

## Harness 体验

Harness 不是一组“按钮 + Prompt + 固定工具流”。目标架构让用户消息、后台心跳、任务事件、复习到期和邮件回复进入同一个耐久 Runtime；Agent 自主选择工具，确定性 Guard 强制权限、频率、预算和安全边界。H2 已落实 UoW、幂等 CAS 与 outbox，H3 已落实统一 lease/phase、终态提交和崩溃恢复，H4 已落实 Evidence/Competency 事实约束；这些边界都不能以 Prompt 或正常路径替代。

前端以 Session 为连续对话主画布和侧栏导航单位；这些交互已有正常路径候选。唯一根 Run 与 late steer 已由 H3 作为耐久后端事实恢复；实时事实顺序、SSE 断线对账、归档焦点清理和提醒 target 仍由 H7-UI-002–005 阻塞。

用户消息编辑已有 Revision 与当前分支候选；目标还要求失效所有下游 Memory/Summary/Snapshot/handoff，并保留完整审计。旧实现漏掉多种 scope/source（H5-CTX-006/007）。

全局对话到计划 Session 的显式承接与可恢复归档是目标契约。旧 handoff 可被后续消息重写，Memory restore 会清空未来 expiry，前端归档可留下 stale focus（H5-CTX-005/011、H7-UI-003）。

计划页面是 Agent 的可操作环境而不是旁路 CRUD 后台。信息架构分为两层：学习计划首页用完整卡片列出所有目标、进度、期限和 Agent 操作概况；点击卡片后进入单一计划工作区，沿纵向时间线查看阶段、任务、证据、复习和操作痕迹。详情不使用横向 Kanban 方格，也不常驻计划列压缩内容；计划路径和 Agent 输入框共享同一视觉中轴。用户从任务行发起的请求仍回到统一 Runtime，由 Agent 先读取上下文再决定是否使用工具。

对话焦点必须显式，不由“最近加载过哪份计划”暗中推断：

- **全局对话**不绑定 `plan_id`，Agent 读取全局画像与跨计划状态，并可通过工具协调多个计划。
- **计划对话**绑定明确的 `plan_id`，Agent 优先读取该计划的任务、事件、记忆、证据和复习安排。
- 进入计划工作区会显示计划焦点；“新对话”始终回到全局焦点。浏览列表、后台刷新和 Run 完成都不能偷偷改变当前页面或焦点。
- 切换焦点使用新的会话边界，避免一个计划的近期原始对话无意进入另一计划；有价值的跨计划结论仍需通过全局记忆候选提升。

统一主 Agent 负责证据、权限和最终写操作；受限子 Run 的 spawn/status/join/cancel 在执行层强制只读白名单。H3 已让 planning 与通用 child 复用统一 lease/checkpoint/retry/budget/finalize 协议，并原子投影或幂等修复父 completion。

## 视觉与游戏化

界面采用 ChatGPT/Codex 桌面端的信息密度与交互协议：浅色侧栏、大面积留白、克制边框、悬浮输入框、消息内 Run disclosure 与 Writing Block 式计划 Artifact。产品导航不照搬通用工作区栏目，而使用学习计划、收件箱、学习记忆、检查学习进度和综合学习上下文等场景语义，并加入轻游戏化基础：

- GitHub 风格学习热力图
- XP、等级和连续学习天数
- 固定规则与 AI 个性化徽章
- 计划进度环、纵向时间线和学习日历
- 跨计划技能树

奖励优先来自有证据的学习行为和考核结果，而不是简单点击。

## 核心使用场景

### 计划与主动提醒

用户从模糊目标开始，经提问卡、规划分工与提案确认创建完整计划。后台心跳读取计划、用户偏好和近期事件，Hy3 自主决定保持安静或发送带具体下一步的提醒。前端展示完整 Agent Run。

### 主动抽查与调整

用户完成核心任务后，Agent 安排并在复习时间主动出题。Hy3 按证据评分，系统更新薄弱点和复习时间，并通过工具调整计划；修改可追踪和撤销。

## 当前产品边界

- 云端多租户、团队协作和移动推送。
- 图片徽章和带任意工具权限的通用多子 Agent 编排；只读规划委员会已经实现。
- 用无限增长的 Prompt 代替上下文管理。
