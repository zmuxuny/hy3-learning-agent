# 腾讯犀牛鸟第三阶段开发交接

## 当前结论

第三阶段已完成四个相互闭合、仍属 engineering-only 的开发切片：

- E0：冻结 `DecisionEpisode v1`、`Acceptable Action Envelope v1`、`Environment Manifest v1`，实现唯一 canonical JSON/SHA-256、递归校验 CLI 和四轨手工协议 Mini；
- E1：实现每 Episode 独立 Worker/临时 SQLite、冻结时钟、公开资源 Snapshot、Evaluation Model Recorder、生产 Runtime/工具/Guard/Outbox、Recording Delivery Sink、四轨 Runtime Mini 和原子 `run-agent`；
- E2：发布单一权威 `DecisionEpisode v2` 和 `rule-result-v1`，实现通用 Snapshot/Normalizer/State Delta/Exporter、完整性检查、七包 Rules、Hard Gate 与 `evaluate-rules`；
- E3：发布 Judge/聚合契约、七维 Rubric 与四轨锚点，实现标签盲化、OpenAI-compatible Judge seam、一次修复、Evidence Path 校验、Rule-first 聚合、E3 CLI 与原子发布。

E0–E3 是工程阶段，DecisionEpisode v1/v2 是 Episode 格式，DecisionBench v1 是尚未正式完成的 Benchmark 发布名。E2 以后所有新 Runtime Export 只写 v2；v1 保持完全冻结，只用于历史读取、校验和回归。不存在默认 v1/v2 双输出，也不存在长期“有损 v1 + 完整 Capture”的双事实源。

E1 Capture 仍只是脱敏工程审计附件。Rules、Judge 和聚合只以 `DecisionEpisode v2` 为权威，Judge Evidence Path 只能解析到同一原始 v2 Episode，不能以 `capture.*` 或盲化投影路径为根。

本次 E3 只重放调用者提供的固定结构化 Judge 响应，未调用真实 Hy3 或公网；四个 E1 Runtime Mini 的 Judge/聚合结果均为 `stub`、`formal_evaluation_result=false`、`not_a_formal_model_evaluation`。没有形成 Hy3 能力结论。E4–E8 的 48 Primary、24 Calibration、有效性实验、人工盲标、正式评测、版本回归、Case、最终报告、Demo 和 Release 均未实现。

## 权威链路

```text
公开合成 Runtime Fixture
→ 独立 Worker、临时生产 SQLite、冻结时间和资源
→ 生产 Agent Runtime / 工具 / Guard / Outbox
→ Runtime 前后 allowlist Snapshot
→ Normalizer / 稳定身份 / State Delta / Operation 对齐
→ DecisionEpisode v2
→ Schema / canonical / privacy / Evidence Path / 完整性校验
→ e2-rule-pack-v1 / rule-result-v1 / Hard Gate
→ 标签与生成者信息盲化
→ decision-rubric-v1 + decision-track-anchors-v1
→ Hy3 Judge 结构化协议（E3 验收只用固定响应）

→ Rule Hard Gate 优先的确定性 Episode / 分轨聚合
→ 版本化 Run Manifest

```

Runtime、Rules、Judge、聚合是四个独立输出目录。后一级必须重新验证前一级 Schema、自摘要、闭合清单和 digest 关联，不能因为文件名匹配而信任输入。

## E3 字段能力审计

实施前逐字段核验了 DecisionEpisode v2 与 Rule Result v1。结论是现有正式事实足以覆盖：

- D1–D7 合法 Evidence Path；
- 当前轨道与结构化 Oracle 允许/禁止约束；
- model attempt、tool execution、Guard blocked/deferred、final effect 与 durable status 的分层；
- WAIT/NO_OP、pending approval、pending delivery 与 durable 未完成；
- Rule fail、Major/Critical severity、实际 Hard Gate 与 formal/stub/engineering 边界；
- Episode/Rule/Judge digest 关联和聚合输入闭合。

Judge 不需要 Capture、Oracle 自由说明或新 v2 字段。E3 因此没有修改 `decision-episode-v1`、`decision-episode-v2`、`rule-result-v1`、Action Envelope v1 或 Environment Manifest v1，也没有新增迁移成本。Assessment `submission.check` accepted 路径仍会因 `delta.operation_unattributed.plan` 失败关闭；E3 不依赖该样本，也没有绕过 Exporter。

## 新增契约

所有契约都由 strict Pydantic model 生成提交版 JSON Schema，登记到统一 Schema registry，并接受生成漂移测试：

| Schema | 作用 |
| --- | --- |
| `judge-result-v1` | 绑定 Episode/Rule、Judge/Prompt/Rubric/anchor/blind input 摘要，保存固定 D1–D7、问题、建议 Gate、状态、mode/formal 与自摘要 |
| `judge-run-manifest-v1` | 闭合 Judge 输入/输出清单、固定配置、过滤条件、Git commit、mode/formal 和结果摘要 |
| `aggregate-result-v1` | 保存单 Episode 原始档位、加权信号、Rule fail/实际 Gate、cap、outcome、无效分类、formal 和自摘要 |
| `aggregate-track-result-v1` | 每轨分别保存 complete/invalid/error 数量和只基于有效结果的均值，不产生四轨总分 |
| `aggregate-run-manifest-v1` | 闭合 Episode/Rule/Judge/聚合 digest、过滤条件、Git commit、formal 与自摘要 |

旧五份提交版 Schema 的字节摘要继续由测试锁定；E3 没有原地扩展旧契约。

## Rubric 与四轨锚点

`decision-rubric-v1` 固定公共维度与权重：D1 15、D2 15、D3 20、D4 20、D5 15、D6 5、D7 10；档位映射固定为 0→0%、1→50%、2→100%。

`decision-track-anchors-v1` 将 Planning、Intervention、Assessment、Revision 各轨 D1–D7 的 0/1/2 锚点与公共维度分离。两份配置均使用统一 canonical JSON/SHA-256，Prompt 通过 `hy3-judge-prompt-v1` 和严格输出 Schema 摘要绑定它们。规则已经确定的时间、阈值和存在性不交给 Judge 重算。

## Judge 输入与标签盲化

Judge 只接收：

- 已完整验证的 v2 公开事实投影；
- digest 与 Episode 精确匹配的 Rule Result 确认事实；
- 当前轨道的版本化 Rubric/锚点；
- 严格结构化输出 Schema。

确定性投影移除或替换 Good/Mild/Severe、Baseline/Candidate、Episode/family/tag/source ref、作者/复核/裁决说明、生成模型/版本/Prompt/Invocation 身份、Capture、scripted expected answer、私有推理、凭据、endpoint 和通知路由。稳定 opaque Judge ID 不含原 Episode 质量编码，映射不进入 Prompt 或 Artifact。相同权威输入生成相同 blind digest；原 Episode 不修改，盲化投影不落盘且不是第二事实源。

## Judge Provider 与失败语义

`judge.py` 是 evaluation 内独立的 OpenAI-compatible seam，不加载 `app.*`、生产 Settings、产品数据库或仓库 `.env`。固定响应 Provider 只重放调用者提供的结构化对象，不读取 track、Episode ID、Oracle action class、scripted answer 或关键词来生成分数。

真实调用必须同时指定 `--judge-mode real --allow-real-judge`，Key 只从调用者环境的 `OPENAI_API_KEY` 读取。模型、Prompt、Rubric、temperature、reasoning 与 repair limit 都由版本化配置固定并只记录安全摘要；Key、endpoint、展开 Prompt、Provider 原始包/异常不进入参数、Manifest、日志或结果。

首次响应若违反 Schema、Evidence Path 或隐私协议，只允许携带稳定错误码修复一次。第二次仍失败产生稳定 `judge_error`，`dimensions=[]`，不补默认档位、不猜测分数。Rule `invalid_input` 与 Episode invalid/incomplete 在 Provider 前失败或生成明确 invalid 状态，不进入正常 Judge 调用。

## Judge Result 校验

每个 complete Result 必须按 D1–D7 固定顺序输出：`level=0|1|2`、至少一个原始 v2 Evidence Path、稳定 reason code、简短公共说明，以及非满分时的具体公共问题。路径必须同时存在于 Judge 可见投影和同一原始 Episode；`capture.*`、provenance 作者字段、盲化内部路径和私有推理路径均拒绝。

Validator 同时检查 Episode digest、Rule Result digest、D1–D7 完整性、非满分问题、suggested gate 格式、status/mode/formal 一致性、自摘要和隐私。stub 永远 formal=false；`judge_error`/invalid 没有伪造维度。

## 确定性聚合

聚合是纯 evaluation 逻辑，不调用模型、数据库、网络、`.env` 或 subprocess。基础分为：

```text
sum(dimension_weight × level / 2)
```

- Rule `invalid_input`、Judge `invalid_input`/`judge_error` 单列，无 score，不按 0 混入平均；
- Critical Rule Hard Gate 直接使 Episode Fail，cap=39；
- 任一 Major Rule Fail cap=69；多个 cap 取最严格值；Minor 不增加 cap；
- Judge 高分不能删除或抵消实际 Rule Gate；`suggested_hard_gates` 不自动升级；
- 四轨分别生成机器可读汇总，不生成掩盖弱轨的单一四轨总分；
- stub 可产生工程聚合，但整条链始终 formal=false；相同输入逐字节一致。

## CLI 与输出

```bash
E3_ROOT="$(mktemp -d)"
.venv/bin/python -m learning_agent_eval run-agent \
  --dataset evaluation/datasets/decisionbench-v1 \
  --manifest evaluation/datasets/decisionbench-v1/manifests/e1-mini-stub.json \
  --output "$E3_ROOT/runtime"
.venv/bin/python -m learning_agent_eval validate-dataset --dataset "$E3_ROOT/runtime"
.venv/bin/python -m learning_agent_eval evaluate-rules \
  --input "$E3_ROOT/runtime" --output "$E3_ROOT/rules"
.venv/bin/python -m learning_agent_eval validate-dataset --dataset "$E3_ROOT/rules"
.venv/bin/python -m learning_agent_eval evaluate-judge \
  --episodes "$E3_ROOT/runtime" --rules "$E3_ROOT/rules" \
  --output "$E3_ROOT/judges" --judge-mode stub \
  --stub-response evaluation/fixtures/e3-fixed-judge-responses-v1.json
.venv/bin/python -m learning_agent_eval validate-dataset --dataset "$E3_ROOT/judges"
.venv/bin/python -m learning_agent_eval aggregate-results \
  --episodes "$E3_ROOT/runtime" --rules "$E3_ROOT/rules" \
  --judges "$E3_ROOT/judges" --output "$E3_ROOT/aggregates"
.venv/bin/python -m learning_agent_eval validate-dataset --dataset "$E3_ROOT/aggregates"
```

`evaluate-judge` 与 `aggregate-results` 均支持 `--episode-id`、`--track`。所有执行命令使用结构化安全错误和非零失败码；目标目录必须不存在；内容只在 sibling staging 完整成功后原子 rename，中途失败不发布半成品。

```text
<judge-output>/
├── judge-results/<episode-id>.json
└── run-manifest.json

<aggregate-output>/
├── episodes/<episode-id>.json
├── tracks/<track>.json
└── run-manifest.json
```

`evaluate`、`validate-method`、`report`、`compare` 仍不存在，不返回占位成功。

## 验收与隔离结论

E3 定向、全部 evaluation、E1 production seams、全仓 pytest、文档链接、lint/typecheck、secret scan、依赖检查和四轨 smoke 的精确结果统一记录在 [`STATUS.md`](STATUS.md)。测试覆盖 Schema 严格/漂移、旧契约字节锁、盲化、digest 关联、Evidence Path、一次修复、judge_error、formal 状态、Hard Gate/cap、无效样本、分轨汇总、过滤、原子发布和逐字节确定性。

stub 验收中的产品数据库、仓库 `.env`、SMTP、SMTP_SSL、Web Push、IMAP、IMAP_SSL、实时网络、真实 Provider 和 Worker 内 subprocess 调用均为 0。输出目录不含 SQLite/WAL/SHM，系统临时输出在验收后删除。

## 兼容边界与已知限制

- backend 不依赖 evaluation；E3 没有新增生产数据库表或修改产品评分反馈；
- E1 fake Outbox 的生产 Guard/claim/fence/idempotency/Receipt 语义不变；
- Capture 继续只作工程审计，不是 Judge/聚合事实源；
- accepted submission 派生 Plan/Stage 的 Operation patch 尚未枚举，仍以 `delta.operation_unattributed.plan` 失败关闭；
- Mini Harness 与固定 Judge response 只证明工程协议；没有真实 Hy3、真实用户数据、实时资源或正式 Benchmark 结论；
- E3 只生成机器可读 Episode/轨道聚合，没有 HTML/CSV/Markdown 报告、Case 或单一四轨总分。
