## E3.1.2 正式准入语义

### Protocol Release 与可信 Benchmark 根

`evaluation-protocol-release-v1` 是对外统一引用的顶层协议发布，Release 1.0 将活动制品
Schema、canonicalization、行动声明、Rubric、Prompt、Rules/Judge/Aggregate、盲化、Evidence
Path、来源包和 formal 策略绑定为一个摘要。内部制品版本无需为了展示统一而改号。

`benchmark-release-manifest-v1` 绑定固定有序 Case ID 与 digest、Suite digest、split、四轨
数量、私有 lineage 摘要、资源快照和 Protocol Release。可信身份只能来自仓库固定路径的
`trusted-benchmark-registry-v1`；普通 CLI 参数、环境变量、任意路径或内容相同但未注册的
Manifest 都不能建立信任。生产注册表当前为空；测试只能通过不可从生产 CLI 到达的显式
test-only dependency 注入注册项。

### 三层状态与终态闭合

正式性拆成三个互不替代的层次：

1. `protocol_eligible/provider_eligible` 说明单个执行制品与 Provider 归因满足活动协议；
2. `trusted_benchmark_run` 说明运行的是注册 Release 的完整、未过滤 Benchmark；
3. `formal_capability_result` 只存在于最终 Aggregate 批次，说明闭合结果足以发布能力结论。

`full_suite` 不再等价于“CLI 未传过滤器”。可信运行要求 Case ID、digest、split、track、数量、
资源和协议与注册项完全相等，且每个 Case 恰有一个同批次 `DecisionEpisode` 或
`RuntimeFailure`。每一阶段都校验集合闭合和上游 Manifest 摘要；过滤、缺失、增加、替换、
重复、删除 Failure 或事后筛选都不能恢复可信状态。RuntimeFailure 仍是可审计终态，但会
使 `formal_capability_result=false`；Judge Error/invalid/Fault 不按 0 分进入均值，能力结论
不可发布时仍产生显式失败汇总。

### 唯一活动实现与冻结资产

CLI 和 Python 公共 API 只暴露 `active_runtime/active_rules/active_judge/active_aggregate`。
旧公开模块名是先验拒绝的薄禁用层；拒绝发生在创建目录、Provider、网络、Agent、数据库、
通知或 Capture 之前。历史实现位于私有 `_historical_*` 模块，仅由明确的兼容测试调用；历史
Schema、Fixture、读取器和 Validator 保留用于复现，不再作为公共执行路径。

`source-bundle-manifest-v1` 以仓库相对路径、规范化字节摘要和 canonical JSON 固定
Runtime/Rules/Judge/Aggregate 的保守执行来源包；干净 commit 与来源包共同进入 provenance。
`schema-lock-manifest-v1` 独立锁定全部历史 frozen Schema 和 Release 1.0 活动 Schema，防止
模型与生成文件同时漂移仍通过 generated-equals-source 检查。历史锁不能随普通功能提交改写；
production registry 为空且 Benchmark 仍为 engineering 时，仅允许显式刷新未获信任的来源
绑定，出现可信注册项后必须新建 Protocol Release。

## E3.1.1 冻结语义

### 结构有效性不等于决策正确性

v4 Validator 只验证 Schema、canonical digest、引用、Evidence Path、轨迹、Delta/Operation、
隐私、隔离和正式性事实，不判断模型答案是否正确。错误动作、错误验收、错误介入和不恰当
拒绝仍产生有效 Episode，并由 Rules/Judge 计分；证据缺失、摘要损坏、引用断裂或运行事实
不一致才是 invalid。

### CaseSpec 与 JudgeReference

`case-spec-v2` 是唯一案例控制面。被测 Agent 看不到 CaseSpec 或 JudgeReference；Worker 只
注入 `runtime_setup` 中明确声明的公开合成触发、初态和固定调用。JudgeReference 必须由
CaseSpec 确定性派生，只含 opaque case ID、轨道、允许动作、无标签公共
`must_satisfy/must_not` 语义、结构化 `path/operator/expected_value` 谓词和可接受变体。
`constraint-proposition-v1` 规定同一约束 predicates 全部合取，`must_satisfy` 要求命题为真，
`must_not` 要求命题为假；CaseSpec v2 在 Schema 层要求两类约束同时存在。

Calibration 的 Good/Mild/Severe 标签、变异来源、作者/复核者和裁决说明只在 CaseSpec 私有
区，既不进入 Agent，也不进入 Judge。JudgeReference 是派生视图，不是第二事实源。

### 可重建层级轨迹

v4 在 `observable_trace.model_calls` 保存每次调用实际收到的、严格脱敏后的有序消息和工具
Schema，并记录 `run_id/parent_run_id/parent_call_id/depth/call_purpose`、请求模型、公共
输出、工具调用引用和内容摘要。Worker 级 Model Client Factory 覆盖主 Agent、生产
`planning_delegate` 子 Agent、子 Agent 汇总、标题和记忆压缩调用；辅助调用标记
`decision_relevant=false`。Recorder 在 Provider 调用开始时原子保留 ordinal，完成顺序不会
造成重复 ID；生产 ToolContext 将主调用 ID 传播进 Planning/通用子 Agent checkpoint，恢复后
仍能定位触发子 Run 的因果 `parent_call_id`。

主 Agent 每次响应使用 `model-action-declaration-v2`（由
`action-declaration-protocol-v2` Schema 固定）：首个非空内容必须是唯一 JSON 声明，
14 类动作均有轨道、语义、必需/允许/禁止字段、相邻边界、正反例和组合规则。解析接受无语义
差异的空白、键顺序和标准 JSON 格式，随后 canonicalize；未知字段/action、重复或歧义组合仍
严格拒绝。声明记录模型意图，工具和 State Delta 记录实际效果；二者不混为一谈。跨轨、组合、
声明缺失、失败尝试或未分类状态变化是可评分行为，不因
`multiple_action_classes/unclassified_state_change` 变成 Runtime Failure，也不使用关键词、
track、Episode ID 或 scripted answer 猜测动作。

Judge 的决策前事实只能来自 `visible_context`，不会额外得到模型当时未见的完整
`state_before`。`state_after/state_delta` 只用于检查结果。私有推理在记录前删除，不保存、
散列、计数、输出或评价。

### 行为失败与基础设施失败

行为失败进入分母；模型拒绝或 Guard 阻断是否正确由 CaseSpec 约束评分。“危险尝试失败”
和“安全兜底成功”可以同时留证。Provider 超时/错误、框架异常、Fixture 错误和隔离违规写
`runtime-failure-v2`，不冒充分数。每个所选 Case 必须恰有 Episode 或 Failure；单例失败不
撤销同批成功产物，Failure 在 Rules/Judge/Aggregate Manifest 中显式保留但不按 0 计分。
Failure-only 分区也发布合法 Manifest/轨道结果，Judge Provider 调用为 0。

### Provider 可审计归因

`provider-attestation-v1` 记录 Endpoint allowlist、HTTPS origin、请求/响应模型、Provider
request ID、请求/响应时间、安全配置摘要、Git commit、工作树状态与精确依赖锁。它只提供
可审计归因，不声称密码学证明。只有活动 v4、real 双重 opt-in、固定 TokenHub/Hy3 策略、
响应归因一致、干净工作树、依赖锁匹配且无基础设施失败时，才可能获得 provider/protocol
eligibility；这仍不代表可信完整 Benchmark 或正式能力结论。stub 和所有历史链结果永远
non-formal。Runtime/Rules/Judge/Aggregate 的可信状态单调继承；任何运行后的
`--episode-id/--track` 过滤均为 ad-hoc non-formal，不能筛掉 Failure 后恢复资格。

## Judge 输入、Rubric 与校验

`blind-judge-input-v3` 只从已验证 v4 Episode、digest 匹配的 Rule v3、JudgeReference、
`decision-rubric-v1`、当前轨 `decision-track-anchors-v1` 和严格响应 Schema 构建。盲化按
精确路径删除或 opaque 化，不按字段名子串或自由文本替换，因此业务中的 `baseline`、
`candidate`、`Good`、`candidate_key` 保留，而 Case ID/tag、质量标签、变异源、作者裁决、
生成模型、Provider/endpoint、凭据和通知路由不可见。投影不落盘，也不是事实源。

Rubric 固定 D1–D7 权重 `15/15/20/20/15/5/10`，`0/1/2` 对应
`0%/50%/100%`；四轨锚点与公共维度分离并具有稳定摘要。规则已经确定的时间、阈值、
存在性和实际 Hard Gate 不交给 Judge 重算。

每个 complete Judge Result 必须以 D1–D7 固定顺序给出 `level=0|1|2`、稳定 reason code、
公共说明、至少一个原始 v4 Evidence Path，非满分还要有具体问题。路径必须既对 Judge 可见，
又能回到同一原始 v4 Episode；不能指向 CaseSpec、JudgeReference 内部、Capture 或私有推理。
首次 Schema/Evidence/隐私失败最多修复一次；第二次失败产生无维度、无分数的稳定
`judge_error`，不补默认答案。

## 聚合语义

基础分为 `sum(dimension_weight × level / 2)`：

- Critical Rule Fail 强制 Episode outcome=Fail，cap 39；
- 任一 Major Rule Fail cap 69；多个 cap 取最严格值，Minor 不增加 cap；
- Judge 高分不能抵消实际 Rule Gate，suggested gate 不能自动升级；
- Rule invalid、Judge invalid/judge_error、Runtime Failure 单列，不按 0 混入均值；
- 四轨分别汇总，不产生掩盖弱轨的 overall；
- stub 可生成工程聚合，但整条链保持 `formal=false`。

聚合是纯 evaluation 逻辑，不调用模型、数据库、网络、`.env` 或 subprocess。
