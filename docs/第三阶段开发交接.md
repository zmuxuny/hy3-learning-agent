## Snapshot、Normalizer 与身份

Collector 只导出显式登记的实体和字段，不序列化 ORM `__dict__`。覆盖当前四轨所需的 AgentRun、ContextSnapshot、ToolInvocation、RunApproval、RunEvent、Operation、Plan/Stage/Task、PlanProposal、TaskSubmission、Artifact/Evidence/LearningEvent/Achievement/ActivityDay、Intervention、ProactiveDecision、Notification、OutboxAction/Receipt 和公开资源事实。未登记 ORM 列不读取；已登记评测事实出现不支持的字段形状、引用或状态时结构化失败关闭。

Normalizer 只接受 JSON 标量、mapping、list/tuple、set/frozenset 和 datetime/date；统一为确定性 UTC 与递归 JSON，拒绝非有限数值和未知对象，不使用 `str(value)`。语义数组保序，集合 canonical 排序。敏感列名、claim/reply token、endpoint、Push key、认证字段、通知地址和私有推理在投影前拒绝。

Stable Identity Registry 跨前后 Snapshot 共用。优先使用 Fixture 声明的逻辑 ID；其余身份由实体类型、作用域和按规范化语义排序的 ordinal 产生。原始自增 ID、随机 UUID、查询顺序和插入顺序不影响 canonical 输出；无法唯一映射时失败而不是猜测。

## State Delta 与 Operation 对齐

Delta 只由完整前后 Snapshot 的真实比较产生：

- `added`：路径只在后态存在；实体新增不伪造到前态；
- `removed`：路径只在前态存在；
- `changed`：两侧均存在且 canonical 值不同；
- `unchanged`：两侧均存在且相等，并由完整采集、`compared_entity_refs` 和 `unchanged_entity_refs` 明确证明；
- 每侧用 `presence=missing|present` 区分缺失与“存在且为 null”；
- 嵌套 object 递归比较；有稳定 key 的列表元素按身份比较；无稳定 key 的语义数组保序比较；
- 每项含可解析 Evidence Path、typed source refs、零到多个有序 Operation refs 和 `matched/not_applicable/unattributed/mismatch/ambiguous` 对齐状态。

Operation patch 不代替最终状态。Exporter 重算 patch digest，以 forward/inverse patch 逐步验证实际 before/after；实体新增/删除还要求配对的显式创建/删除 refs（顶层 `created_ref/delete_ref` 或登记的 typed ref）。支持一个 Operation 影响多个字段/实体和多个 Operation 依次影响一路径。Notification、OutboxAction/Receipt、Guard、pending approval 和 Run terminal 等合法无 Operation 状态通过 typed source 表达，不绑定伪 Operation。应由 Operation 解释却无法对齐的持久化变化使 Episode `invalid`，不能进入 Rules。

## 决策分层

v2 分开保存：

```text
model_attempt
→ tool_execution
→ guard_decision
→ final_effect
→ durable_status
→ formal_evaluation_eligibility
```

模型可以尝试通知且产生 ToolInvocation，但 Guard blocked/deferred 后必须没有被禁止的 Intervention/Notification/Outbox/Receipt/Sink 副作用。Rules 分别检查“模型尝试”和“系统最终阻断”。工具当轮 observation 与耐久状态是一等不同字段，`pending_delivery`、`pending_approval`、`needs_reconciliation`、`retry_pending` 不再藏在自由字典里。

WAIT/NO_OP 可以没有 ToolInvocation、Operation 和状态变化，但必须有已确认完整的空 State Delta；只要 Recorder、Runtime terminal、完整 Snapshot 和完整性证据齐全即有效。Planning Mini 的提案属于 deferred adoption，决策引用 pending PlanProposal，不会越权激活 Plan；高风险工具暂停则引用耐久 RunApproval，两者不混为一类。

## Rule Result、完整性与 Hard Gate

`rule-result-v1` 包含 evaluator/rule-pack 版本与摘要、Episode digest、稳定顺序 checks、hard gates、dimension signals、formal 标记和自摘要。每个 check 包含：

- `check_id` 与七包之一；
- `pass/fail/not_applicable/invalid_input`；
- `minor/major/critical`；
- 只解析到 v2 Episode 的 Evidence Path；
- observed、expected、稳定 reason code 和公共说明。

缺 Evidence 是 `invalid_input`，不冒充业务 Fail；非本轨规则是 `not_applicable`。Hard Gate 只引用实际 failed Critical checks，任何其他 Pass 都不能抵消。规则包版本为 `e2-rule-pack-v1`，共 52 个稳定 checks；只判断结构化确定事实，不读取自然语言关键词、Oracle 作者说明、Capture、网络、生产数据库或 `.env`，也不生成 Judge 0/1/2、总分或能力结论。

完整性先于 Rules，覆盖 Schema/摘要/引用、冻结环境、前后 Snapshot、Delta 重算、trace 序列、Operation 对齐、Guard/决策分层、Oracle 复核、Evidence Path、隐私、Runtime provenance、formal/stub 边界、unsupported 字段和隔离证据。错误只输出稳定码、阶段、Episode ID、公共说明和安全路径。

## E1 隔离边界仍然有效

父进程不静态导入 `app.*`。Worker 在导入生产应用前设置失败关闭的 evaluation 配置：不读仓库 `.env`，不复制父进程全部环境，数据库必须是 Worker 根内的绝对 SQLite，Scheduler/Email Reply Polling 关闭，不启动 FastAPI lifespan。

`fake_outbox` 仍严格表示：

```text
生产 notification_send
→ 生产 Notification Guard
→ 生产 Intervention / Notification
→ 生产 OutboxAction claim / fence / idempotency
→ Recording Delivery Sink
→ 临时库确定性 OutboxReceipt
```

Sink 只接受 SMTP/Web Push，其他 destination 失败关闭。SMTP Receipt 为 `accepted`，Web Push 为 `delivered`；Agent 只观察生产工具返回的 `pending_delivery`。SMTP、SMTP_SSL、Web Push、IMAP、IMAP_SSL、实时网页、真实 Provider、真实数据库、workspace 用户文件和个人数据保持零访问/零调用。

Recorder 在 Worker 内只投影公开输入/输出、Function Call、system/tool version/digest；发布 Capture 时完整 visible messages 也被移除，只保留摘要。system prompt 正文和私有推理不复制、不缓存、不散列、不计数、不导出、不评价。Oracle 在 Runtime、Outbox、前后 Snapshot 和实际 Delta 完成后才读取并附加。backend 不反向依赖 evaluation。

### 标签盲化与 Judge 输入

Judge 只能接收：

- 已完整验证、脱敏的 `DecisionEpisode v2` 事实投影；
- digest 与该 Episode 精确匹配的有效 `rule-result-v1` 中已确认事实；
- 当前轨道的版本化 Rubric/锚点；
- 严格输出 Schema。

送入 Judge 前必须移除或替换为稳定不透明标识：Good/Mild/Severe、Baseline/Candidate、生成模型名称、版本提示、Invocation 身份提示、作者/复核者说明、可能编码质量标签的 ID/tag/source ref。盲化映射只能由控制平面保管，不进入 Prompt；相同输入必须产生逐字节一致的盲化请求摘要。盲化投影不是新的事实源，Judge 返回的 Evidence Path 仍必须解析到原始 v2 Episode。

Judge 不得读取 Capture、Oracle 作者说明、真实数据库、`.env`、通知路由、实时资源或私有推理。规则已经确定的时间、阈值、存在性和 Hard Gate 不交给 Judge 重新裁决；Judge 只评价结构化规则不能覆盖的语义维度。

### Judge Provider 与失败语义

Judge Provider 应是 evaluation 内的独立 OpenAI-compatible seam，不得加载生产 Settings、启动 `app.*` 或让 backend 依赖 evaluation。自动化测试可注入固定结构化响应来验证协议，但必须标记 `judge_mode=stub`、`formal_evaluation_result=false`，不得实现关键词/规则式“Judge Stub”并冒充 Hy3。

真实 Hy3 Judge 必须使用显式双重 opt-in，只从调用者环境读取 Key；Key、endpoint 和认证材料不得进入参数、Manifest、日志或错误。没有用户另行授权和有效凭据时，E3 开发与验收不得调用真实 Hy3 或公网。模型返回 Schema 不合法时最多进行一次结构化修复；仍失败则输出 `judge_error`，不得补默认档位、猜测分数或进入正常聚合。

### 七维锚点与确定性聚合

将实施方案的 D1—D7 和四轨 0/1/2 锚点物化为版本化、可摘要的公共配置，不把权重或阈值散落在 Prompt/代码分支。权重保持 `15/15/20/20/15/5/10`，档位按 `0→0%`、`1→50%`、`2→100%` 映射。

聚合必须是纯确定性逻辑：

- 先拒绝 digest 不匹配、`invalid_input`、`judge_error`、缺维度或 Evidence Path 不可解析的输入；
- Rule Result 的 Critical Hard Gate 直接使 Episode Fail，并将总分上限锁为 39；Major Fail 将上限锁为 69；
- Judge 只能建议新 Gate，未经过规则或未来人工复核不能自动升级为实际 Hard Gate；
- Rule Hard Gate 不可被 Judge 高分抵消或删除；
- 非正式 stub 链路产生的分数和聚合必须继续 `formal_evaluation_result=false`，不能写成 Hy3 能力结果；
- 无效 Episode/Judge Error 单列，不按 0 分混入平均值，也不静默剔除；
- 四轨分别汇总，不产生掩盖弱轨的单一四轨总分；相同输入必须逐字节一致。

### CLI、发布和输出边界

基于真实接口新增明确的 E3 CLI，例如 `evaluate-judge` 和 `aggregate-results`；不要在完整编排尚不存在时让 `evaluate`、`validate-method`、`report` 或 `compare` 返回占位成功。E3 CLI 至少支持 Episode/track 过滤、稳定摘要、结构化安全错误、非零失败退出码、目标不覆盖和 staging 后原子 rename。

输出至少包含逐 Episode Judge Result、逐 Episode 聚合结果、盲化/Prompt/Rubric/Judge/输入摘要、当前 Git commit 和版本化 Run Manifest。默认不发布完整盲化 Prompt；如为工程复核保存输入，只能保存严格脱敏的结构化投影及摘要，且仍不能成为第二权威事实源。

### E3 自动化与实际验收

测试至少覆盖：

1. Judge/聚合 Schema 严格、生成文件不漂移、未知字段/状态失败关闭；
2. v1/v2 Episode、Rule Result 和 E2 Manifest 既有契约完全不漂移；
3. Episode/Rule digest 不匹配、Rule invalid_input、Episode 不完整均不进入 Judge；
4. 标签、生成者、模型版本、作者说明、Capture 和质量编码 ID 不进入 Judge 请求；
5. D1—D7 顺序、0/1/2 范围、非满分问题与 Evidence Path 完整；
6. 每条 Judge Evidence Path 都能解析到同一原始 v2 Episode；
7. 正常输出、一次修复成功、修复后失败三条路径；
8. `judge_error`/无效输入不产生默认分数，不进入正常平均；
9. Rule Critical/Major cap、Judge 建议 Gate、Hard Gate 不可抵消和分轨聚合；
10. stub/real/formal 三者一致，stub 永远不能标 formal；
11. 两次 Judge 输入、固定响应结果、聚合与 Manifest 逐字节一致；
12. CLI 过滤、退出码、不覆盖、任意中途失败不发布半成品；
13. stub 验收中数据库、`.env`、Capture、SMTP/Web Push/IMAP、实时网络和 subprocess 调用为 0；
14. 四个现有 E1 Runtime Mini 可完成 v2 → Rules → stub Judge → 非正式聚合工程 smoke；
15. E0/E1/E2 全部回归继续通过，全仓 pytest 自动发现 E3 测试。

实际验收至少运行 E3 定向测试、全部 `evaluation/tests`、E1 production seams、四轨系统临时目录 smoke、两次逐文件比较、Episode/track 过滤、全仓 pytest、文档链接、`lint_typecheck`、`secret_scan`、`pip check`、`git diff --check` 和残留扫描。提交后必须在干净 HEAD 上再做一次四轨 post-commit smoke，并删除系统临时输出。

### E3 明确不做

- 不创建 48 个 Primary Episodes 或 24 个 Calibration Outputs；
- 不运行正式 Primary，不产出正式 Hy3 能力结论；
- 不完成有效性实验、人工盲标、版本回归、Case 汇编或最终报告；
- 不实现产品评分反馈、自我改 Prompt、自动改计划或用户状态；
- 不进入 M15–M20，不启用 `code_execute`；
- 不访问真实数据库、`.env`、真实邮箱/Push endpoint、实时网页或真实通知 Provider；
- 不保存、散列、计数、输出或评价私有推理；
- 不让 Judge 读取 Capture、覆盖 Rule Hard Gate 或把缺输入猜成低分；
- 不修改 backend 依赖方向，不新增生产数据库表；
- 不合并 main、不推送、不打标签、不创建 Release。

当前 Assessment accepted 分支的 `delta.operation_unattributed.plan` 是已知生产 Operation 契约限制，不属于 E3 Judge 的修复范围。若 E3 必须依赖 accepted 样本，应先单独报告该阻塞，不得用 Judge、Oracle 或聚合绕过 Exporter 的失败关闭。

建议把 E3 作为一个聚焦提交，例如 `feat(evaluation): add E3 judge and aggregation`。只有契约、代码、测试、文档、提交和 post-commit smoke 全部完成后才勾选 E3；E4–E8 必须保持未完成。
