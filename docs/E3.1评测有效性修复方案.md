> `case-spec-v2 → decision-episode-v4/runtime-failure-v2 → rule-result-v3 →

## 1. 目标与边界

E3.1 修复 E0–E3 工程闭环中会影响评测有效性的契约与运行问题。完成后，
DecisionEpisode v3 是唯一可获得正式评测资格的 Episode；DecisionEpisode v1/v2
仅保留为只读、非正式的工程历史回归夹具，不继续扩展，也不建设长期双栈迁移系统。

E3.1 止于正式评测的前置能力、正负与失败 Mini 验证和文档收口。它不生产 48 个
Primary Episode 或 24 个 Calibration Output，不调用真实 Hy3，不执行有效性实验、
正式评测、版本回归、报告、Case 汇编、Demo 或 Release。

## 2. 冻结语义

### 2.1 结构有效性与决策正确性分离

Validator 只确认 Schema、摘要、引用、证据完整性、隐私和运行事实的一致性。动作不在
允许集合、错误验收、错误介入或不恰当拒绝属于有效的行为结果，必须进入 Rules 和 Judge；
它们不是 Episode 结构错误。

以下情况才使 Episode 无效：缺少必要事实、摘要不匹配、引用断裂、轨迹层级损坏、
State Delta/Operation 不对齐、隐私违规或隔离证据不一致。

### 2.2 CaseSpec 与 JudgeReference

`case-spec-v1` 是控制平面的唯一案例事实源。被测 Agent 不读取 CaseSpec；Worker 只把其中
明确标记为运行输入的触发与合成初态注入生产 Runtime。CaseSpec 同时保存：

- 运行配置与显式实体身份绑定；
- 允许动作、判定约束及可接受变体；
- Calibration 质量标签、变异来源和作者裁决等评测私有元数据。

`judge-reference-v1` 必须由 CaseSpec 的判定约束确定性投影生成，不允许独立手写。它只含：

- 稳定不透明案例 ID；
- 轨道与允许动作；
- 无质量标签的公共约束文本；
- 可机器检查的 `path / operator / expected_value`；
- 语义约束的 Evidence Path、criticality 与可接受变体。

质量标签、变异来源、案例原始 ID、作者/复核者和裁决说明不得进入 JudgeReference。
JudgeReference 是 CaseSpec 的派生视图，不是第二事实源。

### 2.3 可重建轨迹

`decision-episode-v3` 保存每次模型调用实际收到的、严格脱敏后的有序消息与工具 Schema，
而不是只保存输入摘要。每个调用记录 `run_id`、`parent_run_id`、`parent_call_id`、深度、
`call_purpose`、是否影响决策、请求模型、公共输出、工具调用引用和内容摘要。

轨迹把决策时输入保存在 `observable_trace.model_calls[*].visible_context`，把工具执行、
Guard、最终效果与持久状态保存在后续结构化字段中。Judge 可以检查事后结果，但不得把
事后状态伪装成 Agent 决策前已经看到的上下文。

私有推理字段不保存、不散列、不计数、不进入 Judge。标题生成和记忆压缩等辅助调用标记为
非决策调用并排除评分；主 Agent、子 Agent 与子 Agent 汇总调用进入可重建父子层级。

### 2.4 行为失败与基础设施失败

行为失败仍产生完整 Episode 并进入分母。模型拒绝或 Guard 阻断是否正确由案例约束评分；
“危险决策失败”和“安全兜底成功”可以同时表达。

Provider 超时、Provider 故障、框架异常、夹具错误或隔离违规产生
`runtime-failure-v1`，不得伪装成模型能力分数。`runtime-run-manifest-v2` 要求每个所选
CaseSpec 恰好对应一个 Episode 或 Failure；单例失败不得删除同批成功制品。Failure 不进入
正常聚合，也不按 0 分混入平均值，但必须显式列出。

### 2.5 Provider 可审计归因

`provider-attestation-v1` 提供可审计归因，不声称密码学证明。它记录并校验：

- 固定 Endpoint allowlist 的版本、摘要、匹配 ID 与 HTTPS Origin；
- 配置模型、逐请求模型、响应模型和 Provider request ID；
- 请求/响应时间、无凭据配置摘要；
- Git commit、工作树洁净状态；
- 运行依赖锁版本与摘要；
- `eligible / ineligible_stub / invalid` 归因状态和稳定原因码。

只有 v3、真实模式、允许的 Endpoint 与模型、响应归因一致、工作树干净、依赖锁匹配且无
基础设施失败的运行才可能获得正式资格。Stub 和所有旧 v1/v2 Episode 永远非正式。

## 3. 版本化契约

| 契约 | 作用 | 正式路径 |
|---|---|---|
| `case-spec-v1` | 唯一案例控制面与私有标注边界 | 是 |
| `judge-reference-v1` | CaseSpec 的确定性、无标签 Judge 投影 | 是 |
| `provider-attestation-v1` | Runtime/Judge Provider 可审计归因 | 是 |
| `environment-manifest-v2` | 依赖锁、洁净提交与 Provider 归因 | 是 |
| `decision-episode-v3` | 可重建、层级化、证据完整的决策记录 | 是，唯一 Episode |
| `runtime-failure-v1` | 基础设施失败的安全终态制品 | 不评分 |
| `runtime-run-manifest-v2` | 所选案例的 Episode/Failure 完整分区 | 是 |
| `rule-result-v2` / Manifest v2 | v3 + JudgeReference 确定性规则 | 是 |
| `judge-result-v2` / Manifest v2 | v3 语义 Judge、一次修复与归因 | 是 |
| `aggregate-result-v2` / Track/Manifest v2 | Hard Gate 优先的确定性聚合 | 是 |
| v1/v2 旧契约 | E0–E3 历史工程回归 | 否 |

所有契约都使用 strict Pydantic、`extra=forbid`、JSON Schema 2020-12、唯一 canonical
JSON/SHA-256 与自摘要。已有 v1/v2 Schema 文件保持逐字节冻结。

## 4. Evidence 与 Judge 输入边界

Judge 输入只可由以下已经验证的结构构造：

- 原始 DecisionEpisode v3 中 Agent 可见轨迹、实际尝试、工具结果、Guard、最终效果与状态；
- 摘要匹配的 Rule Result v2 确认事实；
- 摘要匹配的 JudgeReference；
- 当前轨道的版本化 Rubric 和锚点；
- 严格输出 Schema。

Judge Evidence Path 只能解析到同一原始 DecisionEpisode v3。路径不得指向 CaseSpec、
JudgeReference 投影内部、旧 Capture、私有推理或不存在的自然语言概念。

盲化使用路径级 allowlist/denylist，不做全局词语替换。只删除控制面身份、标签、变异来源、
作者裁决、Provider 身份和路由材料；业务内容中的 `baseline`、`candidate`、`Good` 等词和
`candidate_key` 等业务字段必须原样保留。

## 5. E3.1a–d 实施切片

### E3.1a：语义与契约

- 冻结本文件中的语义与验收矩阵；
- 新增 v3、CaseSpec/JudgeReference、Failure、Provider 和 v2 结果契约；
- 注册并提交 JSON Schema；
- 证明旧 v1/v2 Schema 字节不漂移。

### E3.1b：轨迹与失败终态

- Worker 范围统一 Model Client Factory；
- 主 Agent、子 Agent、汇总与辅助调用按 purpose 记录；
- 保存准确脱敏消息、工具 Schema 和父子层级；
- 每案例独立执行并原子发布批次完整终态；
- 基础设施失败发布安全 Failure，不撤销成功 Episode。

### E3.1c：评测链 v2

- Rules 根据 JudgeReference 评分错误动作，Validator 不判断答案正确性；
- Judge 使用精确路径盲化与实际约束语义；
- 保持一次修复、第二次失败稳定 `judge_error`；
- Aggregate 保持 Rule Hard Gate 优先与 39/69 cap；
- 正确、错误、Guard 安全兜底和运行失败 Mini 端到端验证。

### E3.1d：正式前置硬化与收口

- 锁定 Hy3 Endpoint/请求与响应模型并校验依赖锁和洁净提交；
- 修复相对路径隔离审计与普通业务文本隐私误报；
- 使用显式语义身份绑定，消除多实体排序串号；
- 补齐 Assessment ACCEPT 的 Plan/Stage Operation 对齐；
- 更新全部状态、路线图、实施方案、README 与交接文档。

每个切片通过定向测试后单独提交；E3.1d 后运行完整仓库测试与 post-commit smoke。
