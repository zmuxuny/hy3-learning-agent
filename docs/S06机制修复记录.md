历史证据仍是 [原始 Primary 运行档案](../evaluation/artifacts/e4-candidate-20260905/README.md) 中 `primary-runtime-63be8da.tar.gz` 的 `runtime/failures/failure:primary-s06-p.json`，未改写或重新标记。

|---|---:|---:|---|

| 3 | 20,678 | 16,000 | `planning_intake_update`、`plan_proposal_create` 均标为 `invalid_json` |

历史未保存 malformed 原参数或 `finish_reason`，也没有第四次已完成 Provider 请求；因此不能从 16,000 tokens 推断唯一截断原因，不能重建历史原参数长度、reasoning 长度或当时本地 envelope。公开记录没有 reasoning 字段不意味着当时 Provider 输入没有 reasoning。第二轮重复读取确实增加了上下文，但不足以单独证明终态根因。

独立反例证实：旧 Runtime 将坏 JSON 原文随 assistant 消息放入下一请求，150,000 字符的坏参数能使本地 UTF-8 字节上界超过配置窗口；小坏 JSON 仍可继续。该拒绝来自本地保守估算，不能写成 Provider tokenizer 的实际超窗。正常消息、工具参数、reasoning、工具结果与协议结构现在分别出现在 `request_budget_breakdown.prompt_components`；分项之和等于原有 prompt 上界，计数政策及阈值没有放宽。

## 已实施的机制修复

| 问题与影响 | 文件与行为 | 验证与剩余边界 |
|---|---|---|
| 流式接收忽略 `finish_reason`，完整 JSON 前缀也可能被当成完整响应执行；带 choices 的 usage 会漏读 | [`agent.py`](../backend/app/runtime/agent.py) 在任意 chunk 采集 usage，保留终止原因；并行工具按 index 排序，参数仍逐字拼接。非流式兼容响应传递同一原因 | 覆盖交错分片、转义/中文参数、仅末帧携带原因/usage、真实 Runtime 的流式与非流式两条路径。输出 token 等于上限但 `finish_reason=tool_calls` 的合法响应仍正常执行 |
| 截断回合可能执行部分工具或污染后续请求 | `finish_reason=length` 时整轮工具均不调度；保存 usage 与拒绝证据，下一请求以明确的 Runtime 恢复说明替代该回合，至多一次简短修复；再次截断以 `model_output_truncated` 失败 | 合法 JSON 前缀和坏 JSON 两种截断均无 ToolInvocation/Operation；一次恢复可完成，二次失败保留两次费用与拒绝事件；重启不能绕过次数限制 |
| **P1：最后一轮/最后一次允许调用遇到截断，可能被旧预算 finalization 标为 completed** | 拒绝响应后先核对 step、模型调用和既有运行预算是否还允许修复；预算不允许时直接 `model_output_truncated`，记录 `repair_blocker` 和剩余限制，不声称执行过重试 | `AGENT_MAX_STEPS=1` 与 `AGENT_MAX_MODEL_CALLS=1` 两个独立反例均验证 failed、仅一次已计费响应、没有 run.completed 或 Operation；这是本轮自审追加修复 |
| 巨大坏 JSON 和失败回合 reasoning 原样回放，占满后续上下文 | 新的请求投影只替换已收到 `invalid_arguments` 且语法确为坏 JSON 的参数，保留 UTF-8 长度与 SHA-256 摘要；仅整个工具回合都因坏 JSON 被拒绝时移除其 reasoning。持久化的原消息不被投影改写 | 150,000 字符坏参数可继续，且能修正成一次有效写入；合法长参数、可解析但 schema 错误的参数、有效/混合回合 reasoning 原样保留。合法大历史仍可能触发准确的 `context_window_exceeded`，不声称任意长任务均可恢复 |
| 终态会清理 checkpoint，单靠 checkpoint 无法保留新失败原文 | `model.arguments_rejected` 与 `model.response_rejected` 事件保存完整脱敏失败参数、长度和摘要；截断事件还保存可见 content 与终止原因。事件不参与模型上下文回放 | 运行完成或失败后仍能读取完整失败参数；不保存或广播 private reasoning。旧失败缺失的载荷无法补造 |
| `_fail` rollback 后读取已过期 ORM 属性，可能再触发 `MissingGreenlet`，使失败本身无法收口 | 用 lease 的稳定 run ID；回滚后通过独立会话读取重试次数，后续不访问旧 Run ORM 属性 | 二次截断、重启与合法大历史超窗反例均检验终态。这是新反例证实的独立机制，不据此给旧 S06 追加唯一归因 |
| 原 `_drain_stream` 将 private reasoning 原文广播到 SSE | 保留模型内部所需 reasoning 回放，停止广播原始 reasoning | 流式探针确认 reasoning 可内部返回但不进入可见事件；合法回合原有 reasoning 回放回归继续保留 |

## 验证与执行计划

计划已按“检查历史与机制 → 最小响应/回放修复 → 判别性离线验证 → 交回主流程统一提交和绑定”执行。产品测试在仓库外的源码副本及临时 SQLite 中运行；没有复制 `.env` 或产品运行数据，没有访问原仓库生产库，没有真实模型请求。

专属测试为 [`test_s06_response_recovery.py`](../tests/test_s06_response_recovery.py)、更新后的 [`test_e4_terminal_diagnostics.py`](../tests/test_e4_terminal_diagnostics.py)。H5 envelope、Runtime 状态机、恢复、流式体验、学习闭环与预算广回归 **102 passed / 109.90s**；随后追加合法大历史超窗与两个最后响应边界，最终定向 **28 passed / 11.36s**。两轮有 25 项重合，共验证 105 个不同测试，未把复验次数当成新样本；最后追加的终态修改经过这 28 项定向复验，未重跑前述整组 102 项。新增测试与 prompt envelope 的 Ruff 检查通过，`git diff --check` 通过；Runtime 原文件已有的通用捕获/嵌套 context-manager lint 基线由主流程核对，不将其写成全文件零告警。

未将本修复写成 S06 历史重跑成功。它保证显式 `length` 的拒绝与一次恢复、已确认坏参数的安全回放和终态收口；Provider 未报告终止原因的流结束仍无法仅凭 token usage 判定截断。有效内容持续增长、模型持续生成坏参数或拒绝请求仍可受现有预算/上下文边界终止。后续真实运行属于新源码版本，须保留与旧失败不同的来源绑定。
