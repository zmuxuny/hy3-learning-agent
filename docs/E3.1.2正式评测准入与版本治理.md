# E3.1.2 正式评测准入与版本治理

## 状态与边界

E3.1.2 将 E3.1.1 的活动工程链收敛为 **Evaluation Protocol Release 1.0**，并建立
Benchmark 发布信任根。当前唯一活动链仍是：

```text
case-spec-v2
→ decision-episode-v4 或 runtime-failure-v2
→ rule-result-v3
→ judge-result-v3
→ aggregate-result-v3
```

本轮没有创建 48 个 Primary、24 个 Calibration，没有调用真实 Hy3 或公网，也没有产生
正式能力结论。生产可信 Benchmark 注册表保持为空，因此当前 engineering suite 无论制品
结构多完整、局部 Provider 字段如何声明，都只能是 non-formal。

E3.1.2 完成后的准确结论是：工程上具备申请 E4 数据建设或小规模真实模型协议试跑的
条件；是否进入任一流程仍需单独授权和审查。

## 不可变语义

1. Validator 只判断活动协议下的结构、摘要、引用、证据、来源和批次闭合，不判断模型
   决策是否正确。行为错误进入 Rules/Judge；损坏或不可重建的证据才是 invalid。
2. CaseSpec 是案例控制面；JudgeReference 是由它确定性派生、无质量标签的 Judge 参考。
   被测 Agent 看不到二者，Judge 看不到 Calibration 标签、变异来源、作者或裁决私注。
3. Episode 保存模型实际可见的脱敏消息、工具 Schema 和全部决策相关调用；并发调用以
   稳定因果顺序发布，子 Agent 同时绑定 `parent_run_id` 与 `parent_call_id`。
4. 行为失败是可评分结果；Provider、框架和隔离失败是可审计 RuntimeFailure。每个所选
   Case 必须恰有一个终态，失败不能删除，也不能按 0 分混入均值。
5. Provider Attestation 是可审计归因，不是远端身份的密码学证明。
6. 单个 Episode、Rule Result、Judge Result 或 Aggregate Result 永远不能独立声明完整
   正式评测；只有最终闭合 Aggregate Run Manifest 才能表达能力结论可发布性。

## 发布信任根

### Evaluation Protocol Release 1.0

[`evaluation-protocol-release-1.0.json`](../evaluation/releases/evaluation-protocol-release-1.0.json)
固定以下内容：

- 活动 Case/Episode/Failure/Rules/Judge/Aggregate 与 Run Manifest Schema；
- canonical JSON、SHA-256、Evidence Path 和路径级盲化政策；
- `model-action-declaration-v2`；
- 七维 Rubric、四轨锚点、Judge Prompt/配置和 Rule Pack；
- Runtime、Rules、Judge、Aggregate source bundle digest；
- Schema Lock；
- formal capability 的失败、过滤和四轨报告政策。

制品 Schema 版本与 Protocol Release 版本是两个层次。Release 1.0 对外隐藏内部
v2/v3/v4 组合，但不为了视觉统一改写历史契约。

### Benchmark Release Manifest

`benchmark-release-manifest-v1` 绑定 Release ID/版本、Protocol Release、固定有序 Case、
每个 CaseSpec digest、整体 CaseSuite digest、Primary/Calibration/engineering partition、
四轨数量、私有 mutation/source lineage digest、资源快照、全部协议组件摘要、发布状态、
canonicalization 和 digest 算法。

当前 [`decisionbench-v4-engineering/benchmark-release.json`](../evaluation/datasets/decisionbench-v4-engineering/benchmark-release.json)
状态是 `engineering`，仅用于协议回归。它不是正式 Benchmark Release。

### 生产可信注册表

[`trusted-benchmark-registry-v1.json`](../evaluation/releases/trusted-benchmark-registry-v1.json)
是代码固定的唯一生产信任根，本轮 `entries=[]`。生产 CLI 不接受注册表路径、环境变量、
Release allowlist 或调用者覆盖。内容完全相同但未登记的 Release 也不可信。

测试只能调用名称明确的 `assess_benchmark_release_for_testing`，并传入
`test-only-trusted-benchmark-registry-v1`；该 seam 不被 CLI 或包级公共 API 暴露，且拒绝
伪装成 production registry。

## 三层状态

| 层次 | 代表字段 | 判定范围 | 明确不代表 |
| --- | --- | --- | --- |
| 执行/制品合规 | `protocol_eligible`、`provider_eligible` | 轨迹、Evidence、隔离、固定 Provider/来源政策是否满足 | 官方 Benchmark 完整运行 |
| 正式运行可信 | `trusted_benchmark_run` | 已注册 Release、完整 Suite、无事后过滤、Case/终态闭合、来源与环境一致 | 结果足以发布能力结论 |
| 能力结论可发布 | `formal_capability_result` | 可信运行且无 RuntimeFailure、invalid、judge_error，四轨汇总完整 | 方法已被真实实验验证 |

兼容字段 `formal_evaluation_result` 在单 Episode 和中间阶段固定为 `false`；最终 Aggregate
Manifest 中它只是 `formal_capability_result` 的同值旧名。Validator 不信任自声明布尔值，
而是从生产注册表、Release、Runtime 终态绑定、输入摘要、结果状态和四轨库存重算。

## 完整运行闭合

`full_suite` 不再由“未传过滤参数”推断。可信完整运行必须同时满足：

- Benchmark Release 在生产注册表中，且状态为 `released`；
- Case ID、CaseSpec digest、固定顺序、split、track、数量、资源快照和 Protocol Release
  与注册值完全一致，无缺失、额外、替换或重复；
- Runtime 对每个 Case 发布一个 Episode 或 RuntimeFailure，全部绑定同一个
  `runtime_run_id`、Release 和 Protocol；
- Rules、Judge、Aggregate 的 Episode/Failure 集合与上游闭合，所有 digest 可重算；
- 未进行 `--episode-id` 或 `--track` 事后过滤；
- Git commit、干净工作树、source bundle、依赖锁、隔离和 Provider 条件满足协议。

Aggregate Manifest 保存输入 Runtime Manifest digest 与所选 Runtime terminal records。
Validator 逐 Case 对照注册 Release 的 `case_id/case_spec_sha256/track`，因此修改本地预期
数量、删除 Failure 或只翻转 formal 布尔值不能建立信任。

可信运行中出现 RuntimeFailure 时，Release 来源仍可审计，但
`formal_capability_result=false`，并公开 `capability.runtime_failure`。invalid_input 和
judge_error 同样单列、排除均值并阻止能力结论；失败汇总仍可发布为审计制品，但不得伪造
缺失轨道的正式分数。

## 唯一活动入口与历史资产

公共 CLI 只有：

- `run-agent`；
- `evaluate-rules`；
- `evaluate-judge`；
- `aggregate-results`；
- 只读 `validate-dataset`。

执行入口只指向 `active_runtime.py`、`active_worker.py`、`active_rules.py`、
`active_judge.py` 和 `active_aggregate.py`。旧公共模块是薄的
`legacy_execution_disabled` 适配层：Python 旧 API 在解释调用参数前失败；CLI 只读
检查输入 Manifest 的 Schema 标记后即拒绝历史链。两者都不创建输出、启动 Agent、
调用 Provider、网络、数据库、通知、subprocess 或 Capture。完整历史实现已移入私有
`_historical_*` 模块，只由 test-owned 回归 seam 调用。历史 Schema、Fixture、读取和
Validator 继续保留。

## Source Bundle 与 Schema Lock

四个 source bundle 都保存仓库相对路径、字节长度、文件 SHA-256 和 canonical bundle
SHA-256。Rules/Judge/Aggregate 采用整个 `learning_agent_eval` 包的保守超集；Runtime 还
加入实际生产 `backend/app` Python seam。它们是“评测实现来源包摘要”，不是动态 Python
调用闭包的数学证明。文档、测试、绝对路径、`.env` 和运行时秘密不进入摘要；
源文件按原始字节摘要，所以换行差异也会被明确检出，不做平台隐式归一化。

[`schema-lock-v1.json`](../evaluation/releases/schema-lock-v1.json) 独立锁定全部生成 Schema
的相对路径、Schema ID 与原始字节 SHA-256，并区分 `historical_frozen` 与
`active_release`。所以同时修改 Pydantic 模型和生成 Schema 仍会破坏既有锁；普通功能提交
不得更新历史锁。Release 1.0 提交后，构建脚本只验证，不重写；未来变更必须创建新的
Protocol Release，而不是原地更新 1.0。

## 行动声明协议

[`model-action-declaration-v2.json`](../evaluation/releases/model-action-declaration-v2.json)
是 14 类行动的规范语义词典。每项包含所属轨道、决策语义、必要/允许/禁止字段、相近行动
边界、正反例、允许组合和缺失声明处理。当前行动为：

| Track | Actions |
| --- | --- |
| Planning | `PROPOSE_PLAN`、`REQUEST_USER_INPUT` |
| Intervention | `WAIT`、`INTERVENE_MESSAGE`、`INTERVENE_QUIZ_OR_REVIEW`、`PROPOSE_PLAN_ADJUSTMENT`、`REQUEST_USER_INPUT` |
| Assessment | `ACCEPT`、`REVISION_REQUIRED`、`INSUFFICIENT_EVIDENCE`、`REQUEST_CLARIFICATION` |
| Revision | `NO_OP`、`PROPOSE_CHANGE`、`APPLY_REVERSIBLE_PATCH`、`REQUEST_APPROVAL` |

首个非空内容必须是唯一 `<model-action-v2>...</model-action-v2>` JSON 帧。JSON 空白和对象
字段顺序不影响语义，解析后统一 canonicalize；未知字段/action、重复键/action、重复帧和
未登记组合严格拒绝。缺失或错误声明保留成可评分行为，不让 Episode 在结构层消失。
声明不代替真实 Tool/State Effect，二者不一致由 Rules 记录。

## E4 前的小规模真实协议试跑

本轮不执行该试跑。未来必须由用户单独授权，并先注册专用、非 Primary 的受控试跑 Suite；
建议只验证：

- Hy3 对 14 类行动和相近边界的理解稳定性；
- 首帧结构化声明成功率；
- JSON 一次修复率；
- 缺失、重复、歧义声明率；
- 声明与真实工具调用/状态效果一致率。

试跑结果只能决定协议是否需要新 Release，不能直接扩展成 48 Primary、24 Calibration，
也不能作为能力结论。

## 精确保留债务与删除条件

- `models.py` 仍集中注册历史与活动 Pydantic 模型，`validator.py` 仍统一读取多代制品。
  这是只读兼容边界，不是平行活动执行。只有新 Protocol Release 提供独立迁移器、Schema
  registry 和跨版本 golden corpus 后，才能按版本拆包。
- `active_runtime.py`、`active_rules.py`、`active_judge.py`、`active_aggregate.py` 仍保留占比
  显著的私有旧链分支，以复用 E3.1/E3.1.1 历史回归；它们没有 CLI 或包级公共
  入口，但仍是明确的拆分债务。只有相应历史 golden artifacts 能在不执行旧链的情况下
  完整验证，并且没有测试调用这些 seam 时，才可移出。
- `_historical_runner.py`、`_historical_rule_runner.py`、`_historical_judge.py`、
  `_historical_aggregate.py` 和 `_historical_worker.py` 只承担冻结 Fixture 重建。删除条件是
  历史结果已转为内容寻址 golden corpus、其生成环境被独立归档且回归不再执行旧实现。

上述债务不允许重新接入 CLI、包级公共 API 或 formal 判定。
